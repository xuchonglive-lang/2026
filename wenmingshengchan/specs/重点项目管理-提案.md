# 功能规格说明：重点项目管理

**功能分支**：`[feat-key-project]`  
**创建时间**：2026-04-04  
**状态**：草稿  
**模块类别**：业务核心  

## 一、模块概述
本模块承担了专项、限期且目标相对明确的“重点文明生产项目”的生命周期闭环管理。它包含了管理员分发建档立约、被派发人员过程进展汇报与申请成果验收、以及最终后台的审核结项认定过程。这种模式不仅限于日常监管，涵盖了那些需要花时间并跟踪成果达成的重点项目。

## 二、用户场景与用户故事

### 用户故事 1 - 专项项目的任务立项分解 (优先级：P1)
**场景描述**：当面临上级检查存在突击整改点位时，后台管理员需能够针对这批特定范围的整改事项建立专属工单计划项目并强分派给相关部门及其责任人去集中跟进。
**验收场景**：
1. **假设** 生产部发出针对除尘系统的限时升级指令，**当** 环保主管在后台新建“脱硫装置清灰除尘改进专项”并指定了截止时间和接收的负责人队伍后，**那么** 这些被选中的基层负责人小程序的对应应用端均将能即时查收到这个待推进的新目标。
2. **假设** 立项过程中指定了具体的评分执行与考评标准明细，**当** 项目立项信息保存后，**那么** 未来的所有跟进和终验都需参照这个准绳。

### 用户故事 2 - 执行过程中的定期汇报反馈 (优先级：P1)
**场景描述**：受命进行整改的业务负责人，在周期较长的修复过程期间，需要在手机端定期填写阶段性的推进报告并展示实际场馆变化情况的现场图片，作为工程未落后于进度的强力佐证。
**验收场景**：
1. **假设** 脱硫装置清理工程已开展至第3个工作日，**当** 负责班长进入该项目阶段反馈区域使用该界面的反馈操作提交说明“底槽抽吸已完毕”并附加照片并点送达后，**那么** 此条阶段性信息作为进程轴的节点长存备查且项目总状态保持为“进行中”。
2. **假设** 他仅查看了他人此前上传的过程记录，**当** 数据加载时，**那么** 可以形成一套自上而下的流转记录树，用于后续领导了解中间环节有没有停工卡顿现象。

### 用户故事 3 - 任务完毕提交验收与后侧的最终确认批复 (优先级：P1)
**场景描述**：现场主管确认环境达标后，提出归档结项。后侧管理职能干部收到终验通报后进行评判。若满意则此项重点工作完美终结，反之被驳回需打磨改进。
**验收场景**：
1. **假设** 业务组认为工作全数就位并点击发送“验收闭卷申请”，**当** 相关凭据打包上传完成以后，**那么** 这部分项目的状态立刻变更至“待验收”，一线工人不再能够发起例行的过程性进度汇报。
2. **假设** 管理干部对图片发现有漏扫死角并执行“打回处理附带指导意见”功能后，**那么** 这个专项将退化变更为“进行中”，负责人员会重新看见这个条目需要作善后补扫，进入下一轮迭代验收申请期。

## 三、页面与路由设计

### C端页面设计（mp-client）
1. **项目综合列表与筛查页**：`/pages/keywork/project/list` (含进行中/待验收/已完成等分页卡面切换)
2. **中间过程执行汇报页**：`/pages/keywork/project/process-feed` (包含历史所有步骤的时间轴瀑流展现形式，及用于最新更新填写的表单区段)
3. **成果交付验收申请提交页**：`/pages/keywork/project/apply-finish` (独立的归结界面以示操作庄重点)
4. **终验结论确认及展示结果页**：`/pages/keywork/project/result-view` (一旦进入待验收与之后状态，过程区等屏蔽录入只读并展露这个页面的交互展示状态结论或者退回申斥评语)

### B端页面设计（mp-admin）
1. **统一监控报查分发页面**：`/pages/keywork/project-list` 集合全部业务视角，含添加建立分配项目立项对话框，支持阶段详情流水账细阅，并在达到触发条件时出现验收“放行”与“否决回炉”两个醒目标志按键进行审核结案流转。

## 四、接口与云函数设计

### C端云函数 (`/router/service/client/keywork/`)
- `getProjectList`: 根据登录用户的信息查询关联绑定分派给自己名头或者是名下部门待执行与已执行结束的系列重点作业条目信息。
- `addProcessRecord`: 在项目仍为‘过程推进’标志阶段期间接收与校验处理节点上的情况记录上报，保证数据落盘图元映射合法性。
- `applyProjectClose`: 用户单向发起结项校验。改写表单项目状态至2（待收尾审核态），锁定进一步节点性操作上交凭证。

### B端云函数 (`/router/service/admin/keywork/`)
- `createProject`: 发起、分配关联，生成主干并设置限期倒排等。
- `updateProject`/`closeProject`: 非正常原因撤销或者变更项目周期及基本参数要求。
- `auditProjectResult`: 后台终审判决机制逻辑入口。接见传入态势如果是“否决”，则需将主表写为处理态同时插库一条判决流日志以示拒绝证据；若同意则直接标志“已成功封顶”锁门。

## 五、数据与字段设计

### 1. `key-project` (项目主记录表)
- `_id` 
- `title` (String): 工程名称/标题 
- `area_id`/`point_id` (String): (可选)挂在哪个确切物理位置 
- `standard_desc` (String): 判别达标的文字基准或依据 
- `deadline` (Timestamp): 规章上给定的必须闭卷时刻 
- `assignee_uids` (Array<String>): 负责主导落实这批整改目标的用户们的 ID 集合
- `status` (Number): 0(进行中), 1(待验收), 2(已完成), 3(驳回后进行中) 
- `create_uid`: 立项人的身份指征 
- `audit_remark` (String): 最后一个终局管理者批示的话

### 2. `key-project-process` (从属处理历史节点表库)
- `_id` 
- `project_id` (String): 归属哪头大宗项目关联标记 
- `type` (Number): 1表示中间正常过渡汇报， 2表示申请闭卷交卷单据操作， 3表示管理者下发的拦截驳回指令通告说明节点 
- `desc_content` (String): 富文本叙说当前情况与进度 / 或者驳回责备情况 
- `attachment_imgs` (Array): 照片列 
- `operate_uid` (String): 环节创造者的ID指涉 
- `create_time`: 节点插入钟摆日历 

## 六、核心业务防患与逻辑约束（经头脑风暴确认）

### 1. 数据可见性与权限隔离 (动态推导)
- **B端监控列表可见性**：不强制要求项目归属某一固定部门。在查询项目列表时，后端动态查出当前 B端管理员管辖的部门子树 ID 集合，判断项目中 `assignee_uids` 是否包含隶属于这些部门的用户。只要有交集，该项目对该管理员可见，实现敏捷的人力调度。

### 2. 状态机流转与操作权限 (团队均等与辖区共管)
- **C端申请结项**：宽松模式。`assignee_uids` 数组中的**任何一位执行人**均可代表团队发起结项交卷申请（Type=2）。此时主表锁定进入 `1(待验收)` 状态，前台屏蔽普通节点汇报入口。
- **B端后台终审**：任意能够看到该项目（满足上述可见性推导）的 B端管理员，皆可执行验收。
  - **验收通过**：直接将主表状态变更为 `2(已完成)`，并回写 `audit_remark`。不需要在 `key-project-process` 中额外插入验收成功的记录节点。
  - **验收驳回**：新增一条 Type=3（驳回指令）的 `key-project-process` 记录，并在 C 端时间轴展示打回理由，主表状态退回 `3(驳回后进行中)` 开启下一轮修整。

### 3. 逾期警示判定 (纯前端判断)
- **B端与C端逾期高亮**：是否超期由**前端动态计算**。每次渲染列表或详情时，对比当前客户端时间与主表的 `deadline` 字段。若已超期且 `status !== 2`，前端直接利用工业警示色进行高亮呈现凸显烂尾风险，无需后端记录额外的 `is_overdue` 标识。

### 4. 宪章规范执行
- 全面遵守 Dao 2.0 及 `vk-fun` 云函数调用规范，强制使用 `foreignDB` 执行跨表获取用户信息。
- 每次写操作（状态机变更）必须采取原子性处理。每次生成任何业务实现代码前，必须先规划并运行测试环境（TDD）。
