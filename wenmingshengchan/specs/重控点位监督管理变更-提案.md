# 重控点位监督管理变更提案

**创建时间**：2026-04-21（更新于 2026-04-23：新增指定照片标题需求；更新于 2026-04-29：新增可配置定时触发与反馈时间窗口需求）
**状态**：已确认生效
**背景说明**：
在原有的“重控点位监督管理”模块中，C端一线工友的现场反馈被固化为“1张主图 + N张选填辅图”的模式。同时系统为防范作弊，会在前端强制抓取照片的 EXIF 信息（拍摄时间和设备型号）。
然而，由于微信小程序在 8.0.38 版本后的隐私策略收紧，`chooseMedia` 接口已被抹除所有图片的 EXIF 敏感元数据。基于上述背景，为了降低用户的交互复杂度并彻底解决业务痛点，现需将“强制一张主图和选填多张辅图”的冗余结构，精简并升级为“B端动态指定标题的照片上传槽位”。即：管理员在后台可配置每个重控点要求上传的具体照片标题列表（最多3项，如“现场全貌图”、“整改细节图”），前端根据配置渲染对应槽位并统一验证。

## 变更核心决策
采用 **B端配置驱动 + C端对象数组快照模式**（废弃主辅图分离，启用包含标题的 `images` 对象数组结构）。
放弃对原 `main_image` 及其辅图结构的向后兼容，以绝后患地统一新底层架构，同时去除所有已被微信废弃的 EXIF 读取及校验逻辑。

## 详细变更点说明

### 1. 数据库模型重构 (`key-point-config` 与 `key-point-feedback`)
- **配置表 (`key-point-config`)**：
  - 新增 `photo_requirements`（Array<String>），用于存放必传照片的指定标题列表。数组长度即代表数量要求（最多3项）。示例：`["现场全貌图", "违规细节图"]`。
- **反馈记录表 (`key-point-feedback`)**：
  - **废弃字段**：彻底移除 `main_image`、`sub_images`、`photo_shoot_time`、`device_model` 四个冗余字段。
  - **新增字段**：新增 `images`（Array<Object>）字段。用来存储带有标题和图床URL的对象快照（如 `[{ title: "现场全貌图", url: "..." }]`），确保历史数据防腐性。

### 2. B 端后台配置侧改造 (`mp-admin`)
- **点位配置页 (`pages/feedback/point-config.vue`)**：
  - 废除原有的要求照片数量单选框。实现动态输入列表，管理员可新增具体的照片要求标题（最多3条），前端将其转为 `photo_requirements` 数组提交配置。
- **云函数修改 (`addConfig.js`, `updateConfig.js`)**：
  - 新增对入参 `photo_requirements` 的接收和存库。
- **审批流水列表渲染修改 (`pages/feedback/feedback-list.vue` 等详情弹窗处)**：
  - 必须统一改为：遍历展示 `item.images` 对象数组快照，并在界面上（图片上方或下方）醒目展示该图片的 `title`。
  - 历史脏数据兼容：若遇到旧版纯字符串形式的图片链接数据，应给予默认的“现场照片”占位标题进行防白屏计算。

### 3. C 端前端交互侧改造 (`mp-client`)
- **上传组件大瘦身与槽位拆分 (`pages/feedback/submit/index.vue`)**：
  - 彻底抛弃引入的 `EXIF.js` 相关底层处理代码。
  - 删除分开的“主图区域”与“辅图区域”。拉取到该点位的 `photo_requirements` 后，使用 `v-for` 渲染出带有明确指定标题（如 `*现场全貌图`）的多个独立上传槽位，每个槽位组件单独限制最大上传张数为 1。
- **防线拦截逻辑 (`pages/feedback/submit/index.vue`)**：
  - 在点击“提交反馈”按钮时，遍历检查各个对应槽位是否都已成功上传图片并取得云链接。若有空缺，触发 `vk.toast('请上传[xxx]的照片')` 强制阻断提交请求。
- **云函数修改 (`submitFeedback.js`)**：
  - 去除接收并处理 `main_image`、`sub_images`、`photo_shoot_time`、`device_model` 的参数声明。
  - 改为接收带有 `title` 和 `url` 的 `images` 对象数组快照，并直接存入对应 MongoDB 字段内。

## 风险与防护
因为此提案将物理级抹除原有数据库表结构中的 `main_image` 和 `sub_images` 字段依赖，开发人员在替换 `mp-admin` 后台端各个历史模块时（如重控点位的查看页面组件），务必要一并清查是否有遗漏的旧渲染模型。任何关于图片的读取渲染，必须引入包含短路运算的兼容代码防白屏报错。同时应确保前端提交的图片数组快照总长度不超过设定的最高安全界限（3张）。

## 变更二：可配置定时触发与反馈时间窗口（2026-04-29）

### 背景说明

在原始提案中，定时任务的触发时间和反馈时间窗口均为硬编码逻辑（白班截止 `20:00`，夜班截止 `08:00`，反馈窗口为"每班结束前1小时至每班结束后2小时"）。随着现场运营的深入，管理层需要能够灵活调整这些时间参数以适应不同的排班安排和季节性变化，而无需修改代码或重新部署。

### 变更核心决策

将"定时任务触发时间"和"反馈时间窗口"从硬编码升级为**全局可配置**机制。两个参数按班次（白班/夜班）独立配置，统一对所有反馈任务生效。`feedback_end`（反馈窗口结束时间）同时作为逾期判定的截止线，替代原有的硬编码班次结束时间。

### 详细变更点说明

#### 1. 数据库模型扩展 (`key-point-cron-config`)

在现有的 `key-point-cron-config` 表中新增两个字段：

| 字段名称 | 类型 | 必填 | 示例值 | 说明 |
|---------|------|------|-------|------|
| `feedback_start` | String | ✅ | `19:00` | **新增**。反馈窗口开始时间（HH:mm格式），此时间之前C端禁止提交反馈 |
| `feedback_end` | String | ✅ | `21:00` | **新增**。反馈窗口结束时间（HH:mm格式），此时间之后未提交的任务自动判定为逾期 |

表中固定保持两条记录（白班一条、夜班一条），每条记录同时承载触发时间和反馈窗口，形成完整的班次时间策略：

```json
[
  { "shift_type": "day",   "trigger_time": "14:00", "feedback_start": "19:00", "feedback_end": "21:00" },
  { "shift_type": "night", "trigger_time": "05:00", "feedback_start": "07:00", "feedback_end": "09:00" }
]
```

**时间线示意（以白班为例）**：
- `14:00`（trigger_time）：系统自动生成白班反馈任务。
- `14:00 ~ 19:00`：任务已存在但前端显示"未到反馈时间"，提交按钮禁用。
- `19:00 ~ 21:00`（feedback_start ~ feedback_end）：反馈窗口打开，允许提交。
- `21:00+`：反馈窗口关闭，未提交任务标记为逾期，不可再提交。

#### 2. B 端后台配置侧改造 (`mp-admin`)

- **定时任务配置页 (`pages/feedback/cron-config.vue`)**：
  - 表格新增"反馈开始时间"和"反馈截止时间"两列展示。
  - 编辑表单新增两个 `time` 类型选择器（格式 `HH:mm`），配合必填校验规则。
- **云函数修改 (`setCronConfig.js`, `addCronConfig.js`, `updateCronConfig.js`)**：
  - 新增接收 `feedback_start`、`feedback_end` 参数。
  - 新增校验逻辑：时间格式合法性（`HH:mm`）以及 `feedback_start` 必须早于 `feedback_end`。
  - 将新字段持久化到数据库。

#### 3. C 端云函数核心改造

- **提交反馈 (`submitFeedback.js`)**：
  - **新增时间窗口校验**：提交前先根据任务的 `shift_type` 读取对应 `cron-config` 记录，获取当前服务器时间与 `feedback_start`/`feedback_end` 比对。
  - 若当前时间早于 `feedback_start`：拦截并返回 `"未到反馈时间，请在 XX:XX 之后提交"`。
  - 若当前时间晚于 `feedback_end`：拦截并返回 `"反馈窗口已关闭，任务已逾期"`。
  - 窗口内则正常执行原有的抢答式提交逻辑。
- **待办列表 (`getTodoList.js`)**：
  - **新增窗口状态标注**：批量读取 `cron-config` 构建班次映射表，遍历返回数据为每条任务注入 `_feedback_status` 字段（`waiting` / `active` / `expired`）及具体的 `_feedback_start`、`_feedback_end` 时间值，供前端渲染不同状态的 UI 标签。

#### 4. 逾期判定机制变更

原有的硬编码逾期截止线（白班 `20:00`、夜班 `08:00`）全面替换为基于 `feedback_end` 配置的动态判定：

- **查询时惰性判定**：`getTodoList` / `getHistoryList` 返回数据时，若 `status === 0` 且当前时间已超过 `feedback_end`，动态注入 `status: 2`（逾期态）供前端展示。
- **提交时物理落锁**：`submitFeedback` 在窗口关闭后拒绝提交请求，并可选择将该条记录物理更新为 `status: 2`。

#### 5. C 端前端交互改造

- **待办列表页**：根据 `_feedback_status` 渲染差异化状态标签：灰色"未到反馈时间"、蓝色"可反馈"、红色"已逾期"。
- **提交页**：进入页面时检查状态，若非 `active` 则显示提示信息并禁用提交按钮。

### 风险与防护

1. **跨天窗口**：当前需求明确反馈窗口不跨越自然日（如夜班窗口为 `07:00-09:00`），暂不实现跨天比对逻辑。若未来需要支持（如 `23:00-01:00`），需在时间比对中引入日期偏移计算。
2. **配置校验**：后端必须拦截 `feedback_end` 早于 `feedback_start` 的非法配置。
3. **向后兼容**：若数据库中尚未写入 `feedback_start`/`feedback_end` 字段，云函数应降级为不做窗口校验（允许提交），避免因数据迁移延迟导致服务中断。
4. **实时生效**：配置修改后立即生效。服务端在每次提交时重新读取最新配置，不存在缓存过期的问题。
