# 基础数据管理需求分析变更提案

**创建时间**：2026-04-19
**状态**：已确认生效
**背景说明**：
在原有的基础数据管理架构中，系统通过一个单独的 `department_id` 来承载用户的层级归属。然而在实际工业生产和矿业管理的场景中，部门（如“安环部”）与小组（如“巡检一组”）属于两个独立的管辖维度。如果强行合并在一个字段内，会导致后端列表无法单独剥离出用户的“所属部门”概念，进而导致统计、归类以及数据溯源的失真。

## 变更核心决策
采用 **平铺双字段模式（方案A）**。
放弃对单字段关联或者树状结构向上溯源的复杂封装，选择在存储层面上就直接分离两层概念。

## 详细变更点说明

### 1. 数据库模型重构 (`uni-id-users`)
- **变更前**：仅含 `department_id`（String）。
- **变更后**：
  - 保留 `department_id`（String），并将其语义强制锁定为：用户所属的**一级主导部门 ID**。
  - 增加 `group_id`（String），将其语义定义为：用户在该部门内部所属的**具体生产班组/小组 ID**。

### 2. 注册登记逻辑改造
- **级联面板交互**：前端注册页面（如 `pages/user/register`）在使用 `cascader` 获取选定层级（由于组件特性，通常会输出一个代表层级路径的数组，如 `['部门ID', '小组ID']`）。
- **字段分发落库**：原本的 `updateUserInfo` 云端接口必须将接收到的层级数组解包。第一项存入 `department_id`，若有第二项，则存入 `group_id`。
- **一致性校验**：落库时系统应隐式或显式地担保：存入的 `group_id` 的 `parent_id` 必定等同于一并存入的 `department_id`。

### 3. 数据可视化优化（B端）
- 管理员进入会员列表页后，不再局限于仅显示末端小组信息。
- 表格将分别外联并展示“归属部门”列和“所属小组”列，使行政人员对人员架构的查看一目了然。

## 风险与防护
因为引入了双字段独立记录，开发者务必要在任何发生跨部门人员调动的 API 逻辑中，确保两个字段的同步更新，防止出现类似“部门更新为了行政部，但小组仍遗留为安环部二组”的数据“僵尸缝合怪”现象。该校验将被编织进后续的代码规约之中。
