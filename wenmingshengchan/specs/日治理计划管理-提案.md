# 功能规格说明：日治理计划管理

**功能分支**：`[feat-daily-plan]`  
**创建时间**：2026-04-08  
**最后更新**：2026-04-09  
**状态**：设计完成  
**模块类别**：业务核心  

## 一、模块概述

本模块旨在规范与自动化分配每日的常规修缮、打扫、或点检的"日治理计划"。相比于重控点位的静态打卡策略，日治理计划由各部门的**日计划专业员（计划员）**按日发起，对本部门特定人员或者本部门一批特定人员（按小组）下达执行计划，要求当日完成并上传凭据。

**核心运行逻辑**：
1. 计划员每天早会后在B端创建当日的治理计划，指定执行人员（可按个人多选或按班组整组派发）。
2. 被指定的执行人在C端小程序看到待执行任务，实地完成后上传照片及文字凭证。多人可叠加多次提交反馈。
3. 计划员对已提交的计划进行验收确认（合格/不合格），驳回后执行人可在当日截止前再次补充反馈。
4. 所有用户可透明查看全局当日全部计划的执行情况。
5. 管理层可通过后台多维筛选、统计汇总与Excel导出进行追溯分析。

## 二、角色与权限定义

| 角色 | 标识 | C端权限 | B端权限 |
| --- | --- | --- | --- |
| **系统管理员** | `super_admin` | 全局查看所有计划 | 跨部门查阅与导出所有计划报表 |
| **部门日计划专业员** | `plan_admin` | 查看全局计划 + 在详情页验收本部门计划 | 创建/修改/删除本部门日计划、查看本部门流水、导出报表 |
| **部门普通职工** | `user` | 查看全局计划 + "我的任务"提交反馈 | 无B端权限 |

> **角色说明**：`plan_admin` 为新增独立角色，需追加至 `uni-id-users.role` 数组可选值中。一个用户可同时拥有 `user` 和 `plan_admin` 角色（既是执行人也是计划员）。

## 三、用户场景与用户故事

### 用户故事 1 — 每日计划的定向派发与验收闭环 (优先级：P1)

**用户主体**：部门日计划专业员（计划员）

**场景描述**：每天早会后，计划员结合工作需求，在后台创建当日要落实的具体"小范围修缮打扫事项"，分发给本部门具体班组或指定人员。计划内容包括：计划日期、标题、执行标准内容、区域、执行人、状态。

**优先级理由**：这是整个模块的起点——没有计划派发就没有后续执行与验收流程。

**独立测试**：可通过在B端创建一条日计划并指派给测试用户，然后在C端验证该用户是否收到任务、计划员是否可以验收来独立测试完整闭环。

**验收场景**：

1. **派发计划**：**假设** 计划员新建了一项"清理废弃传送带淤泥"的日计划并指派给"本部门二组"，**那么** 该小组所有活跃成员在小程序的"我的任务"Tab均会看到此待办，计划状态为 **"执行中"**。
2. **验收合格**：**假设** 计划员在C端详情页看到计划状态变为"已提交"，**当** 他点击"验收通过"操作，**那么** 计划最终流转为 **"已完成"** [终态]，所有人不可再操作。
3. **验收驳回**：**假设** 计划员发现执行未达到标准，**当** 他点击"验收不通过"并填写驳回理由，**那么** 计划状态变为 **"未达标"**，执行人可在当日截止前继续补充反馈。
4. **超时未验收**：**假设** 计划以"已提交"状态超过了 `plan_date` 当日 23:59:59 而计划员仍未验收，**那么** 系统将其显示为 **"超时未验收"**；计划员仍可对该状态的计划进行延迟验收，同意→"已完成"，不同意→"未达标"（但因已过截止日，执行人无法再补充反馈，等效为"已逾期"终态）。

---

### 用户故事 2 — 计划的签收执行与多人协作实拍 (优先级：P1)

**用户主体**：被日计划选定的部门职工（可多人）

**场景描述**：承担任务的工人执行任务后，需通过小程序提交完成证明以供考核。多人协作时允许叠加补充证明。每次提交都是追加到反馈流水中，不覆盖之前的提交。

**优先级理由**：这是终端用户最核心的一线操作场景，直接产出现场事实数据。

**独立测试**：可通过创建一条指派给测试班组的计划，让多名测试用户分别提交反馈并验证 `feedbacks` 数组原子性叠加。

**验收场景**：

1. **首次提交与协作**：**假设** 我是二组成员，**当** 我完成清理并提交照片反馈后，**那么** 该计划状态变为 **"已提交"**。随后我所在小组的其他成员**还可以继续提交新的照片反馈信息**（追加到 `feedbacks` 数组中），状态保持"已提交"不变。
2. **被打回重做**：**假设** 我看到计划状态变为 **"未达标"**，**当** 当前日期仍在 `plan_date` 当日，**那么** 我和小组成员依然能继续添加新的补充反馈，状态会再次变为 **"已提交"**。
3. **完成锁定**：**假设** 计划状态变为了 **"已完成"**，**那么** 我和其他成员均不可再添补新反馈，任务正式闭环。
4. **逾期未办失效**：**假设** 当前时间超出了 `plan_date` 当日 23:59:59 且我们尚未提交任何反馈（`status=1`），**那么** 系统将此任务显示为 **"已逾期"** [终态]，不再允许提交反馈。
5. **并发保护**：**假设** A和B几乎同时提交反馈，**当** 云函数处理时使用 `_.push()` 原子追加，**那么** 两条反馈都会完整保存到 `feedbacks` 数组中，互不覆盖。

---

### 用户故事 3 — 数据汇总与历史追踪导出 (优先级：P2)

**用户主体**：所有具备权限的用户（主要是管理员与计划员）

**场景描述**：全局通过多维检索，对历史日计划执行记录与反馈留档进行追溯剖析。

**优先级理由**：数据分析与导出是管理决策的基础，但不阻塞核心业务流程。

**独立测试**：可通过预录入若干不同状态的历史计划数据，在B端验证多维筛选和导出功能。

**验收场景**：

1. **多维聚合筛选**：**假设** 计划员或管理员进入后台日计划管理总台，**当** 按照"日期范围"、"部门"、"状态"、"区域"进行组合检索，**那么** 表格实时刷新展示符合条件的计划列表。
2. **详情追溯**：**假设** 管理员点击某条计划的"展开详情"，**那么** 以时间轴形式展示该计划从派发、多人多次反馈、到最终验收的全部生命周期信息。
3. **报表生成**：**假设** 选定某月1日至月末并过滤出指定部门，**那么** 将展示聚合统计数据（完成率/逾期率/未达标率），且支持一键导出Excel报表。

### 边界情况汇总

| 序号 | 边界条件 | 系统处理方式 |
| --- | --- | --- |
| BC-01 | 计划员创建计划时选择"按班组"派发 | 不固化成员列表，查询时动态展开组内所有活跃成员（`audit_status=3` 且 `status=0`） |
| BC-02 | 按班组派发后，组内有新成员加入 | 新成员自动可见该任务（因为查询是动态展开的） |
| BC-03 | 按班组派发后，组内有成员被禁用 | 被禁用成员自动不可见该任务（活跃成员过滤） |
| BC-04 | 计划员试图修改已有反馈数据的计划 | `feedbacks` 数组非空时，阻止修改计划基础信息，仅允许验收操作 |
| BC-05 | 计划员试图删除已有反馈数据的计划 | `feedbacks` 数组非空时，阻止删除（事实数据不可销毁） |
| BC-06 | 执行人在 `plan_date` 过期后尝试提交反馈 | 云函数检测 `plan_date + 23:59:59 < Date.now()`，拒绝并返回"已逾期，不能提交" |
| BC-07 | 执行人在 `status=2`（已提交）时尝试继续追加反馈 | **允许**：多人可叠加提交，`_.push()` 追加，状态保持 `2` |
| BC-08 | 执行人在 `status=5`（已完成）时尝试提交 | 拒绝，返回"任务已完成，不可再操作" |
| BC-09 | 计划员验收驳回后（`status=3`），但 `plan_date` 已过期 | 执行人尝试再提交时被逾期拦截，等效为终态"已逾期" |
| BC-10 | 超时未验收（`status=2` 且过期）后计划员驳回 | `status` 变为 `3`，但因已过期，执行人无法再提交，等效终态 |
| BC-11 | 非执行人、非计划员试图操作 | 云函数校验身份后拒绝，返回对应权限错误 |

## 四、页面与路由设计

### C端页面设计（mp-client）

#### 4.1 首页汇总概览卡片 (`pages/index/index`)

**功能要素**：
- 在首页 Dashboard 卡片矩阵中新增"日治理计划"概览卡片
- 自动计算并显示当前用户**今日**待执行的计划数量（Tab2 视角的数据）
- 点击卡片跳转至日计划列表页 `/pages/plan/list`

**数据来源**：调用 `client/plan/getTodoCount` 接口，仅传入 token，云端计算返回

**交互细节**：
- 数字为 0 时显示"今日无待办 ✓"
- 数字 > 0 时显示红色角标脉冲动画

---

#### 4.2 日计划列表主页 (`/pages/plan/list`)

**功能要素**：
- **顶部 Tab 栏**（2个Tab）：
  - **Tab 1「全部计划」**：信息共享，展示全局所有部门当日的全部计划，所有用户可见
  - **Tab 2「我的任务」**：仅展示分配给当前用户（或其所在班组）的需执行计划
- **日期筛选条件**：顶部日期选择器，默认今天，可切换查看历史日期的计划

**Tab 1 数据逻辑**：
- 查询条件：`plan_date = 选中日期`，无身份过滤
- 排序：按 `create_time` 降序
- 每条计划项展示：标题、区域名称、部门名称、状态标签、执行人摘要

**Tab 2 数据逻辑**：
- 查询条件：`plan_date = 选中日期` 且当前 `uid` 在执行人范围内
  - `assignee_type='users'`：`uid in assignee_target`
  - `assignee_type='group'`：`uid 所属 department_id in assignee_target`
- 每条计划项展示：标题、区域名称、状态标签、反馈数量

**通用交互**：
- 列表项点击 → 跳转详情页 `/pages/plan/feedback?id={plan_id}`
- 下拉刷新支持
- 状态标签颜色编码：
  - 🟢 执行中(1) | 🔵 已提交(2) | 🟡 未达标(3) | ⚪ 超时未验收(4) | ✅ 已完成(5) | 🔴 已逾期(6)

#### 4.3 日计划详情与操作页 (`/pages/plan/feedback`)

**功能要素**（此页面集成了详情展示、反馈提交、验收操作三合一）：

**区域 A — 计划基础信息展示**：
- 计划标题、区域名称、计划日期、下达人姓名
- 执行标准内容（富文本渲染）
- 执行人列表（按人展示或按组展示组名）
- 当前全局状态标签（含被动感知计算后的真实状态）

**区域 B — 过程反馈流水展示**：
- 以时间轴形式列举所有 `feedbacks` 数组中的反馈记录
- 每条反馈显示：反馈人姓名、反馈时间、照片缩略图（可放大）、文字留言

**区域 C — 验收意见展示**（如有）：
- 展示 `verify_result`：验收人姓名、验收时间、结论（合格/不合格）、评语

**区域 D — 动态交互区域**（底部，按条件显隐）：

| 条件 | 展示内容 |
| --- | --- |
| 我是执行人 且 `status∈{1,3}` 且 `plan_date` 未过期 | 📸 反馈表单：图片上传（最多9张）+ 文字留言 + 提交按钮 |
| 我是 `plan_admin` 且 `status=2` | ✅ 验收合格按钮 + ❌ 验收不通过按钮（附驳回理由输入框） |
| `status=5` 或 `status=6` 或逾期 | 无操作区域，仅展示只读信息 |

**交互细节**：
- 提交反馈：上传照片 + 填写文字 → 调用 `submitFeedback` → 成功后刷新页面
- 验收操作：点击验收按钮 → 弹窗确认（驳回时需填理由）→ 调用 `verifyTask` → 成功后刷新
- 照片上传限制：单张 ≤ 5MB，最多9张
- 提交按钮防抖 2000ms

### B端页面设计（mp-admin）

#### 4.4 日计划管理总台 (`/pages/plan/plan-list`)

**功能要素**（基于 `vk-data-table` + `vk-data-form`）：

**工具栏操作**：
- **新增计划**按钮：打开新增弹窗表单
- **Excel导出**按钮：按当前检索条件导出

**高级检索条件面板**：
| 筛选项 | 组件类型 | 说明 |
| --- | --- | --- |
| 日期范围 | `date-range` | 按 `plan_date` 范围查询 |
| 部门 | `cascader`（仅超管可见） | 关联 `base-dept` 树 |
| 区域 | `remote-select` | 关联 `base-area` |
| 状态 | `select` | 全部 / 执行中 / 已提交 / 未达标 / 已完成 / 已逾期 |

**表格列定义**：
| 列名 | 字段映射 | 说明 |
| --- | --- | --- |
| 日期 | `plan_date` | 计划目标日期 |
| 标题 | `title` | 计划标题 |
| 区域 | `area_name` | foreignDB 展示 `base-area.name` |
| 部门 | `dept_name` | foreignDB 展示 `base-dept.name` |
| 下达人 | `issuer_name` | foreignDB 展示 `uni-id-users.real_name` |
| 执行人 | `assignee_display` | 组模式显示组名，人员模式显示姓名列表 |
| 反馈数 | `feedbacks.length` | 已提交的反馈条数 |
| 状态 | `status` | dict 标签（含被动感知计算后的值） |
| 操作 | — | 详情、编辑（条件可见）、删除（条件可见） |

**新增/编辑弹窗表单字段**：
| 字段标签 | 组件类型 | 数据源 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| 计划标题 | `input` | — | ✅ | 简明扼要的任务摘要 |
| 执行标准 | 富文本编辑器 | — | ✅ | 详细的执行要求与合格标准 |
| 计划日期 | `date` | — | ✅ | 默认今天，截止时间自动为当天 23:59:59 |
| 执行区域 | `remote-select` | `base-area`（`showAll:true`） | ✅ | 关联作业区域 |
| 派发方式 | `radio` | `group`/`users` | ✅ | 按班组 或 按人员 |
| 执行人（班组） | `remote-select` | `base-dept`（本部门下属） | 条件 | `assignee_type='group'` 时显示 |
| 执行人（人员） | `remote-select`（多选） | `uni-id-users`（本部门） | 条件 | `assignee_type='users'` 时显示 |

**详情展开/抽屉模式**：
- 点击"详情"按钮打开 `el-drawer` 侧边抽屉
- 抽屉内容：全生命周期时间轴视图
  - 🟢 创建节点：创建时间、下达人
  - 🔵 反馈节点（多条）：每条反馈的人员、时间、照片、留言
  - ✅/❌ 验收节点：验收人、时间、结论、评语

**权限边界**：
- `plan_admin`：可管理本部门的计划（自动追加 `dept_id` 过滤）
- `super_admin`：跨部门查看所有计划
- 编辑/删除按钮：仅在 `feedbacks` 数组为空时可见

**状态机流转定义**：
```
  [计划员创建]
       │  status = 1
       ▼
  ┌──────────┐
  │ 1·执行中  │─── [执行人提交反馈] ──→ ┌──────────┐
  └──────────┘         _.push()         │ 2·已提交  │←──────┐
       │                                └──────────┘       │
       │                                 │         │       │
       │ (plan_date过期                   │         │       │
       │  被动感知)                [验收通过]  [验收驳回]     │
       │                                 │         │       │
       ▼                                 ▼         ▼       │
  ┌──────────┐                     ┌─────────┐ ┌────────┐  │
  │ 6·已逾期  │←── (plan_date过期) │ 5·已完成 │ │3·未达标│──┘
  │ [终态]    │     被动感知       │ [终态]   │ └────────┘
  └──────────┘                     └─────────┘    │ [执行人
       ▲                                          │  再次提交
       │                                          │  (限期内)]
       └──────────── (plan_date过期) ──────────────┘
```

**被动感知计算状态（display_status）逻辑**：
```javascript
/**
 * 计算展示用状态值
 * @param {Object} plan - 计划记录
 * @returns {Number} 展示状态: 1/2/3/4/5/6
 */
function getDisplayStatus(plan) {
  const deadline = new Date(plan.plan_date + ' 23:59:59').getTime()
  const now = Date.now()
  const isExpired = now > deadline

  // 物理终态直接返回
  if (plan.status === 5) return 5

  // 被动感知逾期
  if (isExpired) {
    if (plan.status === 2) return 4  // 超时未验收
    if (plan.status === 1 || plan.status === 3) return 6  // 已逾期
  }

  // 未过期返回物理状态
  return plan.status
}
```

#### 6.4 `submitFeedback` — 执行人提交反馈 ⭐核心保护接口⭐

| 属性 | 说明 |
| --- | --- |
| **调用场景** | C端详情页反馈表单提交 |
| **输入参数** | `{ plan_id, imgs, remark }` |

**入参校验规则**：
| 参数 | 类型 | 必填 | 校验规则 |
| --- | --- | --- | --- |
| `plan_id` | String | ✅ | 非空，合法ObjectId |
| `imgs` | Array\<String\> | ✅ | 非空数组，长度 1-9，每项为合法云存储路径 |
| `remark` | String | — | 长度 ≤ 2000 字符 |

**3层防护栈处理逻辑**：

| 步骤 | 防护层名称 | 执行逻辑 | 失败返回 |
| --- | --- | --- | --- |
| ① | **身份与权限校验** | 获取 `uid` 和 `department_id`，查询计划记录，校验用户是否在 `assignee_target` 范围内（`users` 模式直接匹配 uid；`group` 模式匹配 `department_id`） | `code: 71003` |
| ② | **状态校验** | 校验计划 `status ∈ {1, 3}`（执行中或未达标），若 `status=2` 也允许（多人叠加），若 `status=5` 拒绝 | `code: 71004` |
| ③ | **时限校验** | 计算 `plan_date + " 23:59:59"` 对应的时间戳，与 `Date.now()` 比对，若已过期则拒绝 | `code: 71001` |

**写入逻辑**（通过所有校验后）：
```javascript
// 原子性操作：追加反馈 + 更新状态
db.collection('daily-plan').doc(plan_id).update({
  feedbacks: _.push({
    uid: uid,
    time: Date.now(),
    imgs: imgs,
    remark: remark
  }),
  status: 2  // 无论之前是1还是3，提交后统一变为2(已提交)
})
```

> **关键：使用 `_.push()` 原子追加**，保障多人并发时 `feedbacks` 数组不会互相覆盖丢失。

**错误码定义**：
| code | 消息 | 触发场景 |
| --- | --- | --- |
| `71001` | 已逾期，不能提交 | `plan_date` 截止时间已过 |
| `71003` | 您不是该任务的指定执行人 | uid 不在 `assignee_target` 范围内 |
| `71004` | 该任务已完成，不可再操作 | `status = 5` |

**成功返回**：
```json
{
  "code": 0,
  "msg": "反馈提交成功"
}
```

## 七、开发逻辑建议与边界防范

### 1. 高频并发反馈的原子性保护
- 核心规则：当更新 `feedbacks` 时**绝对禁止**使用传统的覆盖模型（先读后写），必须使用云数据库自带的 `_.push()` 操作符原子追加子节点
- 确保不同用户在相近时间并发上传时，`feedbacks` 数组完整合并无丢失
- 状态同步更新 `status = 2` 可与 `_.push()` 在同一 `update` 操作中完成

### 2. 权限阻断逻辑
- `status = 5`（已完成）：任何 `submitFeedback` 调用立即抛异常拒绝
- `status ∈ {1, 3}` 且 `plan_date` 已过期：`submitFeedback` 立即拒绝（逾期终态）
- `status ≠ 2`：`verifyTask` 立即拒绝（仅已提交状态可验收）
- 非执行人身份/非计划员角色：对应接口立即拒绝

### 3. 超时/逾期状态的"被动感知"策略
- 与重控点位模块设计一致，**不设**常驻定时扫描脚本修改过期记录状态
- C端/B端查询数据时，实时比对 `plan_date + " 23:59:59"` 与 `Date.now()`：
  - `status=1 或 3` 且已过期 → 展示为"已逾期(6)"
  - `status=2` 且已过期 → 展示为"超时未验收(4)"
- 仅在执行人实际尝试提交时（`submitFeedback`），云函数做硬性拒绝
- 核心优势：**零额外服务器资源开销**

### 4. 按班组派发的动态展开
- `assignee_type='group'` 时，`assignee_target` 存储班组 ID
- 查询"我的任务"时，不展开存储，而是将当前用户的 `department_id` 与 `assignee_target` 做交集匹配
- 优点：人员变动（新增/离职/禁用）自动适应，无需维护快照

### 5. 事实数据不可变原则
- 一旦计划产生了 `feedbacks`（数组非空），计划的基础信息（标题、标准、区域、执行人）不可再修改
- 一旦计划产生了 `feedbacks`，计划不可被删除
- 这保障了反馈凭据与原始要求之间的映射关系不被事后篡改

### 6. 验收结果覆盖写入
- `verify_result` 为单一对象，每次验收操作直接覆盖写入
- 不追溯验收历史，业务只关心最终结论
- 简化数据模型和查询逻辑

### 7. 新增角色 `plan_admin` 的影响范围
- 需在 `uni-id-users.role` 的可选值中追加 `plan_admin`
- 需在 B 端用户管理页面的角色选择器中追加此选项
- 需更新公共核心的 `loginFilter` 或权限校验中间件，使其识别新角色
- C端详情页的验收按钮需依据此角色判断显隐

### 8. 跨时区与时间安全
- 所有时间比对在云端使用 `Date.now()`，**禁止**接受前端传入的时间参数
- `plan_date` 的截止判断统一使用 `new Date(plan_date + ' 23:59:59').getTime()` 计算

### 9. 照片上传规范
- 照片通过 UniCloud 云存储 `uniCloud.uploadFile` 上传
- 存储路径格式建议：`plan/{plan_date}/{plan_id}/{uid}_{timestamp}.jpg`
- 单张限制 ≤ 5MB，单次最多 9 张
- 前端+云端双重校验必填（至少 1 张照片）

### 10. `foreignDB` 关联查询规范
- 所有涉及 `area_id → base-area.name` 的查询必须使用 `foreignDB` + `getOne: true`
- 所有涉及 `issuer_uid → uni-id-users.real_name` 的查询必须使用 `foreignDB` + `getOne: true`
- `feedbacks` 内嵌的 `uid` 关联需在云函数中通过二次查询批量获取姓名（`foreignDB` 不支持数组内嵌对象的直接关联）

## 十、假设

- 系统用户均通过微信小程序接入，拥有稳定的移动网络连接
- 基础数据模块（`base-area`、`base-dept`、`uni-id-users`）已完成开发并有数据可用
- `plan_admin` 角色已在用户管理中可配置
- 计划员每日创建的计划数量 ≤ 50 条/部门
- 系统不需要离线操作能力，所有操作需在线完成
- 照片存储使用 UniCloud 内置云存储服务
- 计划默认仅支持当日或历史日期查看，不支持未来日期的预调度（v1）
