# 功能规格说明：日治理计划管理
**功能分支**：`[feat-daily-plan]`  
**创建时间**：2026-04-04  
**状态**：草稿  
**模块类别**：业务核心  

## 一、模块概述
本模块旨在规范与自动化分配每日的常规修缮、打扫、或点检的“日治理计划”。相比于重控点位的静态打卡策略，日治理计划由各部门的日计划专业角色按日发起，对本部门特定人员或者本部门一批特定人员（按小组）下达的执行计划，要求当日完成并上传凭据。该模块便于归集查看每支队伍当天的执行情况以及计划合规率统计。

## 二、用户场景与用户故事
用户角色划分：

1、系统管理员。

2、某部门日计划专业员

3、某部门普通职工

### 用户故事 1 - 每日计划的定向派发 (优先级：P1)
用户主体：某部门日计划专业员

**场景描述**：每天早会后，某部门日计划专业员结合工作需求，将当日要落实的具体“小范围修缮打扫事项”在后台创建，并分发到本部门具体工段或人员终端账上，计划内容包括：计划时间、计划标题、计划内容（标准）、计划区域、完成时限、计划状态、计划下达人、计划执行人（1人或者多人，可选取某个工段）等。  
**验收场景**：

1. **假设** 某部门计划员新建了一项“清理一车间废弃传送带底部淤泥”的日计划，**当** 他选择指派给“本部门二组”并保存后，**那么** 该小组所有的成员在打开小程序“治理计划”时，均会看到这个强制待办条目，计划状态显示为“执行中”
2. **假设** 某部门计划员在今天登陆系统，当 发现下达的计划状态变成了“已提交”，那么日计划员可以对提交的计划进行同意验收确认操作，计划将变成**“已完成”。**
3. **假设** 某部门计划员在今天登陆系统，当 发现下达的计划状态变成了“已提交”，当发现计划执行未达到标准，那么日计划员可以对提交的计划进行不同意验收确认操作，计划将变成**“未达标”。**
4. **假设** 某部门计划员没有完成同意、或者不同意确认操作，计划以“已提交”的状态超过完成时限，那么计划状态为**“超时未验收”，**日计划员可以对上述状态的计划进行确认操作，如果同意确认，计划将变成**“已完成”，如果不同意确认，计划**将变成**“未达标”。**



### 用户故事 2 - 计划的签收执行与实拍核销 (优先级：P1)
**用户主体：某部门被日计划选定的职工**

**场景描述**：承担任务的工人执行完分配任务后，需通过小程序提交工作完成证明，以便于解除背负的任务并留档考核。  
**验收场景**：

1. **假设** 我是二组成员并负责处理污泥，**当** 我处理完毕通过小程序找到此任务条目，拍摄了干净的现场照片并录毕留言提交后，**那么** 该项计划状态变更为“已提交”，随后我所在小组的其他成员，还可以继续提交新的照片反馈信息。
2. **假设** 我是二组成员，**当** 我登陆小程序看到计划状态变成**“未达标”状态时**，**那么 在计划完成时限之前，我和被选定小组其他的成员，还能继续添加新的反馈，** 下达的计划状态会再次变成了“已提交”。
3. **假设** 我是二组成员，**当** 我登陆小程序看到计划状态变成**“已完成”状态时**，**那么 我和被选定小组其他的成员不能继续添加新的反馈，** 因为下达的计划已经完成。
4. **假设** 我是二组成员，当前时间已经超出了该计划限定的执行日期（如已到第二天），**当** 我和其他二组成员想要补报该治理内容时，**那么** 此任务将不再允许执行操作并沉淀视为“逾期失效”，计划状态显示为“已逾期”。



### 用户故事 3 - 数据汇总与历史追踪导出 (优先级：P2)
**用户主体：所有用户**

**场景描述**：所有用户可以在小程序端按照日期、部门两项信息进行检索日计划数据。  
**验收场景**：

1. **假设** 所用用户，能够具备登陆后台资格的，进入后台历史统计管理页，**当** 设置好从某月1日至月末的查询游标并按具体小组分类过滤后，**那么** 会出现高度浓缩聚合了所有当日发布与响应的数据表格，并一键完成Excel报表的导出生成。

## 三、页面与路由设计

### C端页面设计（mp-client）

#### 3.1 日计划列表/执行主页 (`/pages/plan/list`)
**功能要素**：
- **胶囊 Tabs 分配**：在顶部加入圆角胶囊状的分类 Tabs（全部计划 / 需我执行 / 需要我验收），适配全站极简风格。结合日期与区域检索面板。
- **待执行卡片**：显示标题、区域、下达人、完成时限、状态（执行中/未达标）。点击进入详情执行反馈。
- **需验收卡片**（仅计划员可见）：显示状态（已提交/超时未验收）的计划项。
- **防刷机制**：下拉刷新采用 `z-paging`，默认仅展示当天的任务。如果查询历史，可通过日期挑选。

#### 3.2 日计划详情与反馈页 (`/pages/plan/feedback`)
**功能要素**：
- **基本信息区**：计划标题、所属区域、任务详情/标准（富文本）、下达人、执行人列表、完成时限。
- **反馈记录时间轴**：按时间倒序展示小组内各位成员提报的每一次图文反馈详情。
- **底部操作区（根据身份与状态动态计算）**：
  - **执行人视角**：若状态为“执行中”或“未达标”且未超“完成时限”，显示【添加反馈】操作；超过时限显示灰色【已逾期】。
  - **计划员（验收）视角**：若状态为“已提交”或“超时未验收”，显示【通过验收（已完成）】与【驳回重做（未达标）】按钮组。
  - **添加反馈弹层**：上传照片（主图+辅图）、填写执行说明描述。

### B端页面设计（mp-admin）

#### 3.3 日治理全流程管理台 (`/pages/plan/plan-list`)
**功能要素**（集成 B 端能力，基于 `vk-data-table` + `vk-data-form`）：
- **顶部高级检索**：按日期范围、责任部门（`cascader`树状下钻）、计划状态、下达人/执行人进行组合检索。
- **表格列**：标题、区域（快照/`foreignDB`）、下达人、截止时间、计划状态（`dict`标签）、最后反馈时间、操作列。
- **操作列动作**：
  - **查看详情**：弹窗形式呈现执行人与反馈过程时间轴、历史质检意见。
  - **验收计划**：支持在后台进行通过/驳回动作。
  - **新增计划**：唤出新增表单（只可发布当前至未来日期的单据），表单内下发人员必填且限由所在部门人员选取。
  - **修改/撤回**：仅限状态为“执行中”且未有任何人员反馈的记录，可进行编辑与逻辑删除丢弃。
- **Excel 导出**：基于当前检索条件进行数据聚合导出报表。

## 四、接口与云函数设计

### C端云函数 (`/router/service/client/plan/`)

- `getList`: **核心分发流**，根据入参 `tabType` (todo/audit/all) 及过滤日期，配合当前身份 `uid` 与关联 `dept_id` 进行条件分发。若无日期入参默认锁定今日。所有查询中必须植入“被动感知逾期”逻辑判断，以免去全表跑批定时扫描。
- `getDetail`: 根据 `_id` 获取完整计划、内部流转时间轴（Feedback数组）及验收意见，并以 `foreignDB` 将所涉用户 ID 映射其真实姓名。
- `submitFeedback`: **多接力上交接口**。入参 {`plan_id`, `content`, `images`}。校验计划当前状态是否为允许汇报态，校验时限。原子化采用指令 `dbCmd.push` 将当前汇报人凭据送入内层反馈记录数组，并将外层记录主状态翻转为“已提交(1)”。
- `auditPlan`: **验收流操作接口（下达人/部门管理员层级适用）**。入参 {`plan_id`, `action__(pass/reject)`, `audit_mark`}，状态原子转移并落上验收人及意见戳。

### B端云函数 (`/router/service/admin/plan/`)

- `createPlan`: 后台建单推送，根据选定部门小组和所管辖点位/区域批量配置。可发给“小组全员”，入参校验严格性。
- `updatePlan` / `deletePlan`: 对于派发失误但在“执行中”且且反馈数为 0 的日计划实施字段修正或撤销废弃(逻辑伪删除 `status=-1`)。
- `getAdminList`: 提供包含部门树状数据穿刺下的企业级数据透视图。支持全状态综合追究和管理层数据一键Excel流导出动作。

## 五、数据与字段设计

### `daily-plan` (日治理计划单据表)

本模块以状态机演化单据形式贯穿，**只建一张超级主表**：

| 字段名称 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `_id` | ObjectId | 自动 | — | 主键 |
| `title` | String | ✅ | — | 计划主标题 |
| `content` | String | ✅ | — | 执行标准要求与指示内容（可简化富文本） |
| `area_id` | String | ✅ | — | 相关作业区域（可选则为空） |
| `dept_id` | String | ✅ | — | 发放部门架构追踪溯源 |
| `issuer_uid` | String | ✅ | — | 策划与下达人(发起人) |
| `assignee_ids` | Array\<String\> | ✅ | — | 承接本计划的员工组群 (数组) |
| `deadline_time` | Timestamp | ✅ | — | 必须完成的时间戳节点（红线时限） |
| `status` | Number | ✅ | `0` | **核心状态机**：<br>`0`: 执行中<br>`1`: 已提交(待验收)<br>`2`: 已完成(通过验收)<br>`3`: 未达标(驳回重整)<br>`4`: 已逾期(系统被动判断或强标)<br>`5`: 超时未验收(系统被动判断或强标)<br>`-1`: 已撤销废弃 |
| `feedbacks` | Array\<Object\> | — | `[]` | 反馈与验收流水账面结构如下⬇️ |
| `create_time` | Timestamp | 自动 | — | 发布时间 |

**内部 `feedbacks` 子文档结构（原子追加，全景时间轴）**：
```json
{
  "type": "String (标识状态，如 'submit' 为劳工作业，'audit'为主管批文)",
  "uid": "String (操作人)",
  "time": "Timestamp (操作时间)",
  "content": "String (作业留言陈述，或主管批语)",
  "images": "Array<String> (提交关联的图片，仅 submit 态具有)",
  "action": "String (仅 audit 态具有，如 'pass' 或 'reject')"
}
```

## 六、开发逻辑建议与边界防患

### 1. 以子文档推进消除数据碎片 (Array Sub-document for Feedback)
打破过去“头表+明细表”的关联形式。一条日计划的起落兴衰完整生命周期（含多次接力或重做的全过程历史图文），统一写入进 `daily-plan` 的 `feedbacks` 子文档数组。这依赖于使用 `dbCmd.push()` 结合对象原子更新（不会丢失并发覆盖）。此设计保证一次拉列表不会再请求其它大表，读取速度极高，唯一约束极点明确。

### 2. DDL 惰性洗库策略 (Lazy Timeout Update)
系统 **绝对不要** 写跑批轮询定时任务去主动标记状态 4 与 5。
为彻底规避 B 端复杂检索查不到过期数据的问题：在 C 侧和 B 侧的每一个 `getList` 接口中，第一步执行轻微的 `db.update`：
- 构建更新锁定 `where({ status: dbCmd.in([0, 1]), deadline_time: dbCmd.lt(now) })`
- 根据原状态物理翻转存储为 `4(已逾期)` 或 `5(超时未验收)`。
任何人触发查询瞬间，库中脏数据已被洗净，随后放行真正的外层组合查询。

### 3. 多人接力上报的数据一致性
故事强调“我提交完别人仍可继续提交照片”（如同一班组补充现场视角）。因此云端校验逻辑需开放 `status === 1`（已提交）态依然能在时限前接受内层 `feedbacks` 数组的增添，直至计划下发人点了同意变成 `status === 2` 彻底封盘。系统需使用无锁状态机乐观检查，谨防交叉报错。

### 4. B端大盘的树状下钻查询
日治理计划主要面向自身科室管辖队伍，因此在 B 端的表格一律套用统一封装妥当的“组织架构自顶向下展开透传”（结合 `base-dept` 的树），只要是以 `dept_admin` 角色进入，默认隐式加入 `where: { dept_id: dbCmd.in(本部门及下辖树状层级id集) }`，保证数据不串门越权。
