# 功能规格说明：重控点位监督管理
**功能分支**：`[feat-keypoint-supervision]`  
**创建时间**：2026-04-04  
**状态**：草稿  
**模块类别**：业务核心  

## 一、模块概述
本模块承担系统中最为核心的大并发日常运行——建立现场重控点位与值班责任人员之间的强约束关系。主要目的是能够每天收集重点点位的现场实际情况。逻辑规则：员工每日常规运行两班（白班8:00-20:00，夜班20:00-次日8:00），系统需要规范并要求员工对配置重点点位的现场图像进行上传反馈。每个部门的管理员，在后台配置重点点位与本部门员工的匹配关系（匹配关系包括重点点位id、需每班反馈人员的id结合数组、反馈标准（富文本）、反馈周期，即仅白班反馈，还是夜班反馈，还是白班夜班都反馈、配置下达人），系统通过设定的定时任务，每日定时激活生成任务的云函数，云函数读取系统配置的匹配关系，结合日期时间信息，自动生成当天的重点点位反馈记录，供配置的所有用户进行反馈，所有用户可查询每天实时的现场情况。

## 二、用户场景与用户故事

**用户角色划分：**

1、系统管理员

2、某部门管理员

3、部门某小组员工（多人）

4、所有用户

### 用户故事 1 - 系统配置定时任务 (优先级：P1)
**用户主体：系统管理员**

**场景描述**：现场采用白班（8:00-20:00）与夜班（20:00-8:00）两班倒。反馈要求白班和夜班都要形成反馈数据，系统管理可以配置定时任务的时间，定时任务定时激发系统中的云函数，形成每班的现场反馈信息。

**验收场景**：

1. **假设** 系统管理员需要配置定时任务时间。**当** 系统管理员登录后台管理系统后，**那么** 在系统中的定时任务配置页面，可以新增、修改时间，定时间任务更新后，按照既定时间定时执行云函数，自动生成当天的重点点位反馈记录，供配置的所有用户进行反馈。

### 用户故事 2- 配置重点点位与本部门员工的匹配关系 (优先级：P1)
**用户主体：某部门管理员**

**场景描述**：现场采用白班（8:00-20:00）与夜班（20:00-8:00）两班倒。某部门管理员结合现场需要重点管控的点位信息，用于配置重点点位反馈匹配关系。

**验收场景**：

1. **假设** 某部门管理员认为现场某一个点位比较重要，需要掌握现场的实际情况。**当** 某部门管理员登录后台管理系统后，**那么** 在系统中进行新增与修改、删除（假删除）重点点位反馈匹配关系，匹配关系包括重点点位id、需每班反馈人员的id结合数组、反馈标准（富文本）、反馈周期，即仅白班反馈，还是夜班反馈，还是白班夜班都反馈、配置下达人。
2. **假设** 定时任务在规定的时间读取了配置的重点点位反馈匹配关系，**那么** 激发云函数，自动生成当天的重点点位反馈记录，供配置的所有用户进行反馈。重点点位反馈记录包括：日期、班次、区域id、点位id、 反馈执行人ids（小组成员）、任务下达人id、部门id（任务人的部门）、匹配关系id、现场反馈信息（富文本）、状态（执行中、已完成、已逾期）。

### 用户故事 3- 用户获取任务，执行反馈任务 (优先级：P1)
**用户主体：部门某小组员工（多人）**

**场景描述**：现场采用白班（8:00-20:00）与夜班（20:00-8:00）两班倒。在每班结束前1小时，至每班结束后2小时内，部门某小组的员工可以在登陆系统后，对需要自己反馈的任务进行反馈。提前反馈会弹出还未到反馈时间，滞后会弹出已逾期，不能提交的消息。另外，每个任务虽然设置了多个执行人，但是只要一个执行人完成了反馈，那么这个任务就算结束，不需要其他人反馈人。

**验收场景**：

1. **假设** 部门某小组员工今天在上班。**当** 定时任务在规定的时间出发反馈记录生成机制，**那么** 部门某小组员工登陆小程序后，小程序上会标注需要自己反馈的任务数量，在每班结束前1小时，至每班结束后2小时内，对需要自己反馈的任务进行反馈。提前反馈会弹出还未到反馈时间，滞后会弹出已逾期，不能提交的消息。另外，每个任务虽然设置了多个执行人，但是只要一个执行人完成了反馈，那么这个任务就算结束，不需要其他人反馈人。

### 用户故事 4 - 重控点位反馈信息共享 (优先级：P1)
**用户主体：所有用户**

**场景描述**：所有用户都能在首页点击查看每天、本班、每个区域、每个点位的现场情况。  

**验收场景**：

1. **假设** 我登陆系统，点击现场重点点位报表，转向一个页面，**当** 我不选择信息时，就默认显示上个班次的最新信息，当我选择日期、班次、区域、点位后，**那么** 就按照检索条件显示现场的信息。

## 四、接口与云函数设计

本模块的所有云函数接口设计均参考强依赖于 `vk-fun` 技能规范，依托 `vk-unicloud-router` 框架构建。使用 `vk.baseDao` 处理常规 CRUD；处理并发生态时调用底层更新原子级支持锁机制。

### C端云函数 (`/router/service/client/feedback/`)

- `getTodoCount`: **首页待办数统计**。运用 `vk.baseDao.count()` 根据当前时间判断所处班次与窗口期，通过 `uid` 去 `key-point-feedback` 查询 `status=0` 且在本人认领名下的记录数。可标注为“预览”态或“待办”态。
- `getTodoList`: **获取个人分发任务列表**。结合当前属于白班还是夜班时段，找出归属于当前登录 `uid` 下需要提交点位，若时间不到窗口期返回“未到时间”锁定标识。查询采用惰性计算，将由于逾期的记录动态转态展示。
- `submitFeedback`: **录入事实依据**。底仓操作完全摒弃先查后改的模式，基于 `vk-fun` 中的事务理念或原子更新方案：`await vk.baseDao.update({ where: { _id: id, status: 0 }, data: { status: 1, ... } })` 形成无锁抢答防并发踩踏。若返回的 `updated` 影响行数为 0，则由 router 抛出阻断弹窗告知该项已被同组旁人代为报结。
- `getDetail`: **全景详细查阅**。单体 `findById` 提取详情，并通过配置连表及用户映射表 (`uni-id-users`) 拉取提报人真实姓名及头像快照。
- `getHistoryList`: **大盘透明查询流**。以动态组拼 `where` 进行区域、点位过滤，并在返回后注入前置的补时运算阻断被动逾期状态，返回统一分页模型。

### B端云函数 (`/router/service/admin/feedback/`)

- `addConfig` / `updateConfig` / `deleteConfig` / `getConfigList`: **基础关系映射维护池**。依赖 `vk-fun` 表栏自动绑定机制进行基本增删改；`dept_admin` 角色在触发 `getConfigList` 时使用高级对象化注入查询参数截断隔离查询越界(`where.dept_id = _.in(userDeptTree)`)。
- `getFeedbackList`: **监管层流水大盘**。赋予带有科室级部门树状下穿隔离查询 (`JQL` 或直接由 `vk-fun` 内部过滤拼接)。支持结合日期范围、点位等多维定位。
- `auditFeedback`: **质检与通报标注**。提供后台查看反馈照片后的违章标记留底，更新至单据内容中作为闭环管理。
- `setCronConfig` / `getCronConfig`: **定时分发策略配管**。支持 B端动态改变白班/夜班的生成推流基准时间（HH:mm），将变更沉淀至 `key-point-cron-config` 内，打通前端化配管而无需修改代码平台触发器。

### 定时任务云函数

> **参考文档**：[UniCloud 云函数定时任务规范](https://vkdoc.fsq.pub/client/uniCloud/cloudfunctions/timer.html)

- `generateFeedbackTasks`: **动态卡点发放机**。配置在 UniCloud 的 Crontab 触发器（`package.json` 中的 `triggers`）可设定为高频空转（如 `0 */5 * * * *` 每5分钟一次）。触发后脚本内部不直接发单，而是首先读取 `key-point-cron-config` 中各班次设定的触发时间（HH:mm）。与当前系统时间差值在容错阈值内且当前无推流记录时，遍历检索 `key-point-config` 并打包调用 `vk.baseDao.adds` 生成当日的快照副本到 `key-point-feedback`。底座依赖联合唯一索引防御多次命中下的双重发包。

## 六、开发逻辑建议与边界防患

### 1. 照片元数据 (EXIF) 防伪与溯源机制
为防止员工用以前的老照片、“翻拍账单照片”应付差事，系统不在 C 端强制索取 GPS，而是利用 `exif.js` 技术进行**影像留痕弱校验**。
- **获取机制**：前端 (`submit` 页) 在用户完成照片选择（非原生相机强制时，有极大概率从相册取旧图）后，在推流 OSS 前使用 `EXIF.js` 拦截读取图像 Header 数据。提取其原始拍摄时间 (`DateTimeOriginal`) 和 相机型号 (`Model`)。
- **上报沉淀**：将抓取到的真实时间随表单同传给 `submitFeedback` 并固化到表中。后台质检员在察看流水时，肉眼即可比对“单据按期提交时间”和“提取的真实拍摄时间”是否大跳跃，作为虚假考勤打卡的判定铁证。

### 2. 抢答式防并发踩踏机制
用户故事明确“由于设置多个执行人，只要一个执行人完成了反馈，那么任务就算结束不需其他人反馈”。
云函数的提交逻辑必须彻底摈弃“先查后改”的设计缺陷。直接依赖 `vk-fun` 中的基础机制机制，实施高并发下无锁安全的条件写入：
`await vk.baseDao.update({ where: { _id: target, status: 0 }, data: { status: 1, submit_uid: currentUid } })`
如返回影响的行数为 0，这代表在并行时间窗内被工友捷足先登夺魁，服务器即退回阻断响应：“该任务已被同组人员完成”，保证资源隔离且图床垃圾不冗余。

### 3. 夜班顺延与时间窗口约束
鉴于夜班往往贯穿跨日历变更(夜间20:00 - 清晨08:00)，云端脚本必须引入单独抽离剥离出来的公共 ShiftContext 时间计算器以校准时间误差。
- **归属延迟结算设定**：强制规定所有夜班归卷的数据账单 `shift_date`，都以**下班跨越的次日日期**为统一落定值。
- **合法期“一刀切”硬收束**：不设置任何宽限时间与交班缓冲。白班截止线即严格的 `20:00:00`，夜班即严格的 `08:00:00`。踩点跨界后前后端实施零容忍硬封锁，强制标记为逾期。

### 4. DDL 惰性感知洗库策略 (Lazy Status Update)
系统中的硬性核验环节决不能使用庞大后台脚本轮训库区标记“超期态”(浪费海量RU与计算时效)。
与“日治理计划逻辑”高度协同一致：当流水检索（`getTodoList`, `getHistoryList`）与客户端抓取详情被叫响时，代码中实时做基于 `Date.now()` 的零容差软过滤拦截；只要超载过了标准下班时点而原始记位依然在 `0`，则直接动态压入 `2` 作为页面呈现（伪装状态传递）。直到真正有逃逸前端时限请求想要进行 `update` 时，服务后端引擎基于同样判定再将其一掌落入物理状态 `2` 锁定。此机制为最高级别之查询瘦身。

### 5. Cron并发双擎的幂等保险
UniCloud 云函数定时任务容许调度系统存在秒间双重激活导致任务下放错乱之风险。（详参定时任务容错文档）。
故必须、绝对必须于 MongoDB 的 `key-point-feedback` 上打下唯一重烙印（复合索引）：
`db.collection.createIndex({ config_id: 1, shift_date: 1, shift_type: 1 }, { unique: true })`
从而令二次执行的批量 `adds` 操作由于锁冲突自动崩溃并由上层 `try-catch` 做安静回收化平，将逻辑内耗根除于无形中。

### 5. 组级树状鉴权机制贯彻落实
遵循全局规约：所有对基础数据 `getList` 的抓取都要带着组织隔离边界操作。`dept_admin` 进入查询必须强制获取他关联在 `base-dept` 底下的树层，在 `where` 里附加 `_.in([全树子代节点])` 从而将其它独立厂区的秘密截断。任何组件表格透传，底层同服此列。
