# 功能规格说明：重控点位监督管理

**功能分支**：`[feat-keypoint-supervision]`  
**创建时间**：2026-04-04  
**最后更新**：2026-04-09  
**状态**：设计完成  
**模块类别**：业务核心  

## 一、模块概述

本模块承担系统中最为核心的大并发日常运行——建立现场重控点位与值班责任人员之间的强约束关系。主要目的是通过系统化的配置与定时驱动，每天自动收集重点点位的现场实际情况。

**核心运行逻辑**：
1. 员工每日常规运行两班制：白班（8:00-20:00）、夜班（20:00-次日8:00）。
2. 各部门管理员在后台配置"重控点位反馈匹配关系"（绑定点位、责任人/小组、反馈标准、班次频率、配置下达人）。
3. 系统管理员配置定时任务触发时间，系统通过定时云函数读取匹配关系，按日期和班次自动**预生成**当班的反馈任务记录。
4. 相关责任人在规定的反馈时窗内（每班结束前1小时至结束后2小时）登录小程序提交现场照片与文字反馈。每个任务仅需一名执行人完成即视为闭环（**抢答式核销**）。
5. 所有用户可通过多维筛选查询每天、每班、每个区域、每个点位的现场反馈情况。

## 二、角色与权限定义

| 角色 | 标识 | C端权限 | B端权限 |
| --- | --- | --- | --- |
| **系统管理员** | `super_admin` | 全局概览、查询所有反馈 | 配置定时任务、跨部门查看所有配置与反馈流水、质检标注 |
| **部门管理员** | `dept_admin` | 本部门概览、查询本部门反馈 | 配置本部门重控点位匹配关系、查看本部门反馈流水、质检标注 |
| **普通员工** | `user` | 查看个人待办、提交反馈、查询所有历史反馈（信息共享） | 无B端权限 |

## 三、用户场景与用户故事

### 用户故事 1 — 系统配置定时任务 (优先级：P1)

**用户主体**：系统管理员

**场景描述**：现场采用白班（8:00-20:00）与夜班（20:00-8:00）两班倒。反馈要求白班和夜班都要形成反馈数据，系统管理员可以在后台配置定时任务的触发时间。定时任务按照既定时间定时执行云函数，根据匹配关系配置自动生成每班的现场反馈任务记录。

**优先级理由**：定时任务是整个模块的驱动引擎，不配置定时任务则无法自动生成反馈任务，整个模块将无法运行。

**独立测试**：可通过在后台配置定时任务触发时间并手动触发一次 cron 云函数来独立测试，验证反馈记录是否按预期被批量生成。

**验收场景**：

1. **假设** 系统管理员需要配置定时任务时间，**当** 系统管理员登录后台管理系统进入"定时任务配置"页面，**那么** 可以分别设置白班任务生成时间（如 7:50）和夜班任务生成时间（如 19:50），保存后定时任务将按新时间执行。
2. **假设** 定时任务在配置时间（7:50）被触发，**当** 云函数执行时，**那么** 系统读取所有状态为启用的匹配关系配置，筛选出 `require_shifts` 包含 `day` 的配置项，为每条配置生成一条当日白班的待反馈记录（`status=0`），已存在的记录不重复生成（幂等保护）。
3. **假设** 系统管理员暂时停用了某班次的定时任务，**当** 到达原触发时间时，**那么** 云函数不执行，当班不生成任何新的反馈任务。

### 用户故事 2 — 配置重控点位与部门员工的匹配关系 (优先级：P1)

**用户主体**：部门管理员

**场景描述**：部门管理员结合现场需要重点管控的点位信息，在后台配置"重控点位反馈匹配关系"。匹配关系定义了哪些人负责哪些点位、按什么标准反馈、反馈频率是白班还是夜班或两者皆要。

**优先级理由**：匹配关系配置是定时任务生成反馈记录的数据源，没有配置就没有任务可生成。

**独立测试**：可通过在B端"重控点配置"页面新增、修改、禁用匹配关系来独立验证配置CRUD功能，并在下一次定时任务触发后确认反馈记录是否按新配置生成。

**验收场景**：

1. **假设** 某部门管理员认为现场某一个点位比较重要，需要掌握现场实际情况，**当** 该管理员登录后台管理系统进入"重控点配置"页面，**那么** 可以新增一条匹配关系，包含：选择重控点位、选择本部门的反馈人员（支持多选）、填写反馈标准（富文本）、选择反馈周期（仅白班 / 仅夜班 / 白班夜班都反馈）。系统自动记录配置下达人为当前操作管理员。
2. **假设** 管理员新增了一条匹配关系配置，**当** 下一次定时任务按规定时间触发时，**那么** 云函数读取到该新配置并自动生成对应的反馈任务记录，供配置中的所有指定用户在反馈时窗内进行反馈。
3. **假设** 管理员需要调整某条匹配关系（如更换反馈人员），**当** 修改并保存后，**那么** 已生成的历史反馈记录不受影响，仅后续新生成的任务按新配置执行。
4. **假设** 管理员对某条不再需要的匹配关系执行删除操作，**当** 系统处理时，**那么** 执行逻辑删除（设 `status=0` 禁用），该条配置不再参与后续定时任务生成，但历史关联的反馈数据留存不销毁。

### 用户故事 3 — 用户获取任务并执行反馈 (优先级：P1)

**用户主体**：部门某小组员工（多人）

**场景描述**：在每班结束前1小时至每班结束后2小时内（白班反馈窗口 19:00-22:00，夜班反馈窗口 07:00-10:00），部门某小组的员工登录小程序后，对系统自动生成的待反馈任务进行现场照片和文字反馈。每个任务配置了多个执行人，但只需一个执行人完成反馈即视为任务闭环（**抢答式核销**）。

**优先级理由**：这是终端用户最核心的一线操作场景，直接产出现场事实数据。

**独立测试**：可通过注入测试数据（创建status=0的反馈记录），模拟窗口期内外不同时间点进行提交并验证时窗拦截逻辑和抢答式核销。

**验收场景**：

1. **正常反馈**：**假设** 部门某小组员工今天值白班，定时任务已在7:50生成了白班反馈任务，**当** 该员工在19:30（窗口期内）登录小程序，**那么** 首页概览卡片显示"待反馈：N"，点击进入待办列表可看到所有需要本人反馈的点位任务。
2. **提交反馈**：**假设** 员工选择某个待办任务进入反馈表单页，**当** 拍摄1张主照片、最多5张辅助照片并填写文字描述后点击提交，**那么** 系统校验时窗合法后将反馈数据原子性写入记录，任务状态变为"已完成"（`status=1`）。
3. **提前反馈阻断**：**假设** 员工在18:00（未到19:00窗口期）尝试提交反馈，**当** 系统进行时窗校验时，**那么** 弹出提示"还未到反馈时间，请在本班结束前1小时至结束后2小时内提交"，阻止提交。
4. **逾期反馈阻断**：**假设** 员工在22:30（超出22:00窗口期）尝试提交白班反馈，**当** 系统进行时窗校验时，**那么** 弹出提示"已逾期，不能提交"，阻止提交。
5. **抢答式核销**：**假设** 某任务指定了A、B、C三名执行人，**当** A率先在窗口期内成功提交反馈后，**那么** B和C再查看待办列表时该任务不再出现（或显示为"已由A完成"并置灰），无需重复反馈。
6. **并发保护**：**假设** A和B几乎同时点击提交同一任务的反馈，**当** 云函数处理时利用 `where: { status: 0 }` 条件更新，**那么** 仅第一个到达的请求成功写入，第二个因状态已变更而被拒绝并返回"该任务已由他人完成"提示。

### 用户故事 4 — 重控点位反馈信息共享查阅 (优先级：P1)

**用户主体**：所有用户

**场景描述**：所有用户都能在首页点击进入"现场重点点位报表"页面，查看每天、每班、每个区域、每个点位的现场反馈情况。默认显示上个班次的最新信息，也可通过日期、班次、区域、点位等筛选条件进行精准查询。

**优先级理由**：信息透明共享是本模块的核心价值输出，满足管理层与一线员工对现场情况的实时掌握需求。

**独立测试**：可通过预录入若干反馈记录并在历史查询页面分别测试默认展示、条件筛选、详情查看等功能独立验证。

**验收场景**：

1. **默认展示**：**假设** 我登录系统后点击首页的"现场点位报表"入口，**当** 不选择任何筛选条件时，**那么** 默认显示上一个已结束班次的所有反馈信息（包含已完成和已逾期的记录）。
2. **条件筛选**：**假设** 我在报表页面选择了日期=4月8日、班次=白班、区域=洗选厂，**当** 执行搜索后，**那么** 页面仅展示4月8日白班洗选厂下所有点位的反馈数据。
3. **详情查看**：**假设** 我在列表中点击某条已完成的反馈记录，**当** 进入详情展示时，**那么** 可以看到反馈人姓名、反馈时间、反馈照片（可放大查看）、文字描述、以及该点位的反馈标准对照信息。

### 用户故事 5 — 全局管控与照片质检核验 (优先级：P2)

**用户主体**：系统管理员 / 部门管理员

**场景描述**：管理人员通过后台反馈报表，利用多维度筛选穿透复核一线员工上传的证据材料质量，并对不合规的反馈做出批示整改标注。

**优先级理由**：质检是保障反馈数据真实性的管理闭环手段，但不阻塞核心反馈流程，优先级次之。

**独立测试**：可通过在B端反馈流水页面筛选已完成记录，对其进行质检标注操作来独立验证。

**验收场景**：

1. **照片核验**：**假设** 管理员通过后台反馈流水页，筛选本月3号洗选厂的所有照片上传记录，**当** 发现某张照片是黑图或不符合标准，**那么** 系统允许在该条目留言标注"不达标"并记录扣分说明，可追查其所属的具体人员或小组。
2. **数据导出**：**假设** 管理员需要月度统计报表，**当** 设定筛选条件并点击导出，**那么** 系统生成包含反馈完成率、逾期率、质检结果的Excel文档下载。

### 边界情况汇总

| 序号 | 边界条件 | 系统处理方式 |
| --- | --- | --- |
| BC-01 | 定时任务执行时某匹配关系配置刚被禁用 | 该配置不参与本次生成，已生成的历史记录不受影响 |
| BC-02 | 定时任务执行后管理员新增了匹配关系 | 本班次不会追补生成，需等到下一次定时触发才生效 |
| BC-03 | 同一配置的同一班次同一日期记录已存在 | 通过复合唯一索引 `config_id + shift_date + shift_type` 阻止重复生成，cron 做静默跳过 |
| BC-04 | 夜班跨自然日（20:00-次日8:00）的日期归属 | 采用 **夜班归属后延法则**：夜班的 `shift_date` 统一归入夜班结束日（次日日期）。如4月9日20:00-4月10日8:00的夜班，其 `shift_date = "2026-04-10"` |
| BC-05 | 员工手机本地时间被篡改 | 所有时间校验全部在云端执行，依赖 `Date.now()` 作为唯一时间基准，前端不传任何时间参数 |
| BC-06 | 网络波动导致重复提交 | 前端防抖节流（2000ms）+ 云端条件更新原子性（`where: { status: 0 }`）双重保护 |
| BC-07 | 匹配关系中的某个责任人账号被禁用 | 该用户不再出现在待办列表中（查询时联合检查 `audit_status=3` 活跃状态），但已完成的历史反馈不受影响 |
| BC-08 | 反馈窗口外发现现场异常 | 系统阻断本模块提交，界面引导用户前往【报备信息管理：异常隐患库】提交突发异常，保证本模块数据的纯洁性 |
| BC-09 | 同一点位被多条配置关联（不同部门/不同小组） | 各配置独立生成各自的反馈记录，互不干扰 |
| BC-10 | 定时任务云函数执行超时或异常中断 | 逐条 `try-catch` + 唯一索引幂等保护，已成功的记录不受影响，下次触发可安全重跑补全 |

## 四、页面与路由设计

### C端页面设计（mp-client）

#### 4.1 首页汇总概览卡片 (`pages/index/index`)

**功能要素**：
- 在首页 Dashboard 卡片矩阵中新增"重控点位"概览卡片
- 自动计算并显示当前用户在**当前最近班次**的待反馈任务数量
- 点击卡片跳转至待办列表页 `/pages/feedback/todo-list`

**数据来源**：调用 `client/feedback/getTodoCount` 接口，仅传入用户 token，由云端计算返回数字

**交互细节**：
- 数字为 0 时卡片正常展示"已全部完成 ✓"绿色标注
- 数字 > 0 时显示红色角标脉冲动画提示
- 非反馈窗口期仍展示下一个班次的预览数量，但标注"（预览）"字样提示用户

---

#### 4.2 待办考点列表页 (`/pages/feedback/todo-list`)

**功能要素**：
- 展示当前用户在当前班次的所有待反馈任务列表
- 每条任务项显示：点位名称、区域名称、反馈标准摘要（截取前50字）、任务下达人姓名、当前状态标签
- 状态标签：🟢**待反馈**（可操作）| 🔵**已完成**（"已由XX完成"，置灰）| 🔴**已逾期**（超时未完成，置灰）
- 顶部显示当前班次信息标题，如"白班 2026-04-09"

**交互细节**：
- 列表项点击路由逻辑：
  - `status=0` 且 `in_window=true` → 跳转至反馈提交页 `/pages/feedback/submit?id={feedback_id}`
  - `status=0` 且 `in_window=false`（未到）→ Toast 提示"还未到反馈时间"
  - `status=0` 且 `in_window=false`（已过）→ Toast 提示"已逾期，不能提交"
  - `status=1`（已完成）→ 跳转至详情展示（只读模式）`/pages/feedback/history?detail_id={feedback_id}`
- 支持下拉刷新（重新调用 `getTodoList` 接口）

#### 4.3 现场反馈表单页 (`/pages/feedback/submit`)

**功能要素**：
- 顶部展示任务基本信息区：点位名称、区域名称、反馈标准（富文本渲染显示完整内容）
- 核心表单区域：
  - **主照片**上传（必填，1张，建议强制实时拍摄模式）
  - **辅助照片**上传（选填，最多5张）
  - **文字描述**输入（选填，`textarea` 纯文本或简易富文本）
- 底部提交按钮

**入参**：`id` = 反馈记录 `_id`（从待办列表页传入 URL query）

**交互细节**：
- 页面 `onLoad` 时云端再次校验时窗合法性，若不合法直接拦截弹窗并 `navigateBack`
- 照片使用微信原生 `uni.chooseImage({ sourceType: ['camera'] })` 强制实时拍摄模式（可补充 'album' 作为降级选项）
- 照片上传前做前端压缩（限制 ≤ 5MB/张）
- 提交前弹出二次确认弹窗：显示照片缩略图和提交摘要
- 提交过程中按钮显示 Loading 状态并禁用（前端防抖 2000ms），防止重复点击
- 提交成功后 `Toast` 提示"提交成功"并自动 `navigateBack` 返回待办列表（自动刷新）
- 提交失败时根据错误码显示对应提示文案

## 六、接口与云函数设计

### 核心公共引擎：班次上下文计算器

在所有关键接口调用前，需要一个统一的班次上下文计算器 `getShiftContext()`，作为**独立工具函数**提取至 `/router/service/common/` 或 `unimodules` 公共基础类中复用。

```javascript
/**
 * getShiftContext() — 班次上下文计算器
 * 
 * 输入：当前服务器时间 Date.now()（禁止接受前端传参）
 * 
 * 输出对象结构：
 * {
 *   current_date: "YYYY-MM-DD",           // 当前自然日
 *   shift_date: "YYYY-MM-DD",             // 当前班次归属日期
 *   shift_type: "day" | "night",          // 当前班次类型
 *   in_window: Boolean,                    // 是否在反馈窗口期内
 *   window_start: Timestamp,              // 当前班次窗口期开始时间戳
 *   window_end: Timestamp,                // 当前班次窗口期结束时间戳
 *   prev_shift_date: "YYYY-MM-DD",        // 上一个已结束班次的归属日期
 *   prev_shift_type: "day" | "night",     // 上一个已结束班次类型
 *   next_shift_date: "YYYY-MM-DD",        // 下一个班次的归属日期
 *   next_shift_type: "day" | "night"      // 下一个班次类型
 * }
 * 
 * ═══════════════════════════════════════════════════════════════
 *  时间段划分逻辑（24小时完整覆盖，对应中国时区 UTC+8）
 * ═══════════════════════════════════════════════════════════════
 *  
 *  00:00 ~ 07:00  →  前日夜班（尚未进入反馈窗口）
 *                    shift_date = 今日, shift_type = "night"
 *                    in_window = false
 *                    prev: 前日白班
 * 
 *  07:00 ~ 10:00  →  前日夜班反馈窗口期
 *                    shift_date = 今日, shift_type = "night"
 *                    in_window = true ★
 *                    prev: 前日白班
 * 
 *  10:00 ~ 19:00  →  今日白班（尚未进入反馈窗口）
 *                    shift_date = 今日, shift_type = "day"
 *                    in_window = false
 *                    prev: 今日夜班(shift_date=今日)
 * 
 *  19:00 ~ 22:00  →  今日白班反馈窗口期
 *                    shift_date = 今日, shift_type = "day"
 *                    in_window = true ★
 *                    prev: 今日夜班(shift_date=今日)
 * 
 *  22:00 ~ 24:00  →  今日夜班（尚未进入反馈窗口）
 *                    shift_date = 明日, shift_type = "night"
 *                    in_window = false
 *                    prev: 今日白班
 * 
 * ═══════════════════════════════════════════════════════════════
 *  关键法则 — 夜班归属后延：
 *  夜班（20:00至次日8:00）的 shift_date 统一规定为夜班结束日（次日）。
 *  例如 4月9日20:00-4月10日8:00，shift_date = "2026-04-10"
 * ═══════════════════════════════════════════════════════════════
 */
```

### C端云函数 (`/router/service/client/feedback/`)

#### 6.1 `getTodoCount` — 首页待办数量统计

| 属性 | 说明 |
| --- | --- |
| **调用场景** | C端首页概览卡片加载时 |
| **输入参数** | 无（仅依赖 token 解析 `uid`） |
| **鉴权** | `uid` 必须存在且 `audit_status=3`（已审核通过） |

**处理逻辑**：
1. 调用 `getShiftContext()` 获取当前班次上下文 `{ shift_date, shift_type, in_window }`
2. 查询 `key-point-feedback`：
   ```
   where: {
     shift_date: shift_date,
     shift_type: shift_type,
     status: 0,
     assignee_ids: dbCmd.in([uid])
   }
   ```
3. 执行 `count()` 返回待办数量
4. 若 `in_window === false`：在返回数据中标注 `is_preview: true`，提示前端此为预览数据

**返回结构**：
```json
{
  "code": 0,
  "data": {
    "count": 3,
```

#### 6.3 `submitFeedback` — 提交现场反馈 ⭐核心保护接口⭐

| 属性 | 说明 |
| --- | --- |
| **调用场景** | C端反馈表单页提交 |
| **输入参数** | `{ feedback_id, main_image, sub_images, content }` |

**入参校验规则**：
| 参数 | 类型 | 必填 | 校验规则 |
| --- | --- | --- | --- |
| `feedback_id` | String | ✅ | 非空，合法ObjectId格式 |
| `main_image` | String | ✅ | 非空，合法云存储路径 |
| `sub_images` | Array\<String\> | — | 数组长度 ≤ 5，每项为合法云存储路径 |
| `content` | String | — | 长度 ≤ 2000字符 |

**5层防护栈处理逻辑**：

| 步骤 | 防护层名称 | 执行逻辑 | 失败返回 |
| --- | --- | --- | --- |
| ① | **身份校验** | 校验 token 有效性，获取 `uid`，检查 `audit_status=3` | `code: 401` |
| ② | **时窗校验** | 调用 `getShiftContext()`，校验 `in_window === true`；若 `false` 判断是提前还是逾期，返回对应错误码 | `code: 70001` 或 `70002` |
| ③ | **权限校验** | 查询 `feedback_id` 对应记录，校验 `uid` 是否存在于 `assignee_ids` 数组中 | `code: 70003` |
| ④ | **状态校验** | 校验查询到的记录 `status === 0`（待反馈），若已完成或已逾期则拒绝 | `code: 70004` |
| ⑤ | **原子性写入** | 使用**条件更新**实现抢答防并发：<br>`db.collection('key-point-feedback').where({ _id: feedback_id, status: 0 }).update({ status: 1, submit_uid: uid, submit_time: Date.now(), main_image, sub_images, content })`<br>检查 `updated` 返回值，若 `=== 0` 表示被他人抢先 | `code: 70004` |

**错误码定义**：
| code | 消息 | 触发场景 |
| --- | --- | --- |
| `70001` | 还未到反馈时间，请在本班结束前1小时至结束后2小时内提交 | 窗口期未开始 |
| `70002` | 已逾期，不能提交 | 窗口期已结束 |
| `70003` | 您不是该任务的指定执行人 | uid 不在 assignee_ids 中 |
| `70004` | 该任务已由他人完成 | status ≠ 0 或原子更新 updated=0 |

**成功返回**：
```json
{
  "code": 0,
  "msg": "反馈提交成功"
}
```

```
          config_id:          config._id,

          point_name:         快照名称,
```

## 七、开发逻辑建议与边界防范

### 1. 班次时段处理的独立性与复用性
- `getShiftContext()` 函数必须作为**独立工具方法**提取至 `/router/service/common/shift-utils.js` 或 `unimodules` 公共基础类中
- 所有 feedback 模块的云函数统一引用此工具方法
- 所有时间计算均依赖 `Date.now()`（服务端），**绝对禁止**接收或使用前端传入的本地时间参数

### 2. 防并发抢答的原子性保护
- 提交反馈时必须使用**条件更新**模式：`where: { _id, status: 0 }` + `update`
- 利用 `updateAndReturn` 或检查 `updated` 返回值，`updated === 0` 表明数据已被他人修改
- 前端同时实施**防抖节流**（2000ms 间隔），禁止提交按钮被重复点击
- 网络异常时前端不自动重试提交，显示"请稍后手动重试"

### 3. 定时任务的幂等性设计
- 复合唯一索引 `config_id + shift_date + shift_type` 是系统防止重复数据的最后一道屏障
- 每条插入操作用 `try-catch` 独立包裹，唯一索引冲突时执行**静默跳过**（`skip_count++`），不中断整批任务
- 即使 cron 被意外触发多次、网络超时后重试，也保证数据不重复

### 4. 逾期状态的"被动感知"策略
- 与日治理计划模块设计保持一致，**不设**常驻定时扫描脚本循环修改过期记录状态
- 查询接口内实时比对当前服务器时间与班次窗口期终点时间：
  - 白班窗口终点：`shift_date 当日 22:00`
  - 夜班窗口终点：`shift_date 当日 10:00`
- 若 `status===0` 且已过窗口期 → 返回给前端时标注为逾期
- 仅在用户实际尝试提交（触发 `submitFeedback`）时，云函数做硬性拒绝并**可选地**将 `status` 原子性更新为 `2`
- 此方案的核心优势：**零额外服务器资源开销**，逾期标识随查询自然浮现

### 5. 数据快照与不可变原则
- 反馈记录由 cron 生成时，从 config 中快照冗余以下字段：`point_name, area_name, feedback_standard, assignee_ids, issuer_uid`
- 后续对配置的修改**不影响**已生成的历史反馈记录
- 这保障了事实数据的**历史可追溯性**——即使点位改名、人员变更，已有反馈记录依然如实反映当时状态

### 6. 权限隔离与组织架构穿透
- B端所有需要数据隔离的接口，对 `dept_admin` 角色自动追加组织架构树过滤条件
- 隔离逻辑：传入操作人 `department_id` → 递归 `base-dept` 获取自身 + 所有级联子部门/班组 ID 集 → 拼接为 `dbCmd.in([...ids])` 条件
- 复用公共核心模块已定义的"树状下钻隔离"方案，不重复造轮子

### 7. 照片上传与存储规范
- 照片通过 UniCloud 云存储 `uniCloud.uploadFile` 上传
- 存储路径格式建议：`feedback/{shift_date}/{point_id}/{uid}_{timestamp}.jpg`
- **限制**：单张图片 ≤ 5MB，上传前可在前端做质量压缩
- 主照片必填校验在**前端**和**云函数**双重执行（前端优化体验，云端保障安全）
- 建议优先使用 `sourceType: ['camera']` 拍照模式，减少从相册上传旧照片的可能

### 8. 夜班跨日边界的统一处理
- 夜班始终使用**后延归属日期法则**：`shift_date` = 夜班结束日（次日自然日）
- 此法则必须贯穿所有涉及日期计算的场景：定时任务生成、待办查询、历史查询、统计汇总、被动感知逾期计算
- 典型示例对照：
  | 实际时间 | shift_date | shift_type | 说明 |
  | --- | --- | --- | --- |
  | 4月9日 07:50（cron触发生成白班任务） | 2026-04-09 | day | 今日白班 |
  | 4月9日 19:30（用户提交白班反馈） | 2026-04-09 | day | 今日白班窗口期 |
  | 4月9日 19:50（cron触发生成夜班任务） | 2026-04-10 | night | 后延至明日 |
  | 4月10日 08:30（用户提交夜班反馈） | 2026-04-10 | night | 夜班窗口期内 |

### 9. 配置变更后的生效边界
- 新增/修改的配置在**下一次定时任务执行后**才会生效（当班已生成记录不追补）
- 禁用的配置立即停止参与后续 cron 生成，但已生成未完成的任务**仍允许**被正常提交
- 若确有业务需要当班即时追补生成，可在 `addConfig` 接口中追加"当班即时生成"逻辑（标注为 **P3 可选** 增强项）

### 10. 反馈窗口外异常处理引导
- 当用户在非窗口期通过本模块尝试提交却被拦截时，前端应展示醒目的引导操作提示
- 引导文案建议："当前不在反馈时段内，如发现现场异常请前往【异常隐患报备】提交"
- 此设计保证本模块数据的**纯洁性**——每条反馈记录严格对应其所属班次的规定窗口期

## 九、成功标准

| 编号 | 可衡量指标 |
| --- | --- |
| **SC-001** | 定时任务在配置时间触发后 **30秒内** 完成所有反馈记录批量生成（日常配置量 ≤ 200条） |
| **SC-002** | 用户从打开待办列表到完成反馈提交，全流程操作时间 **≤ 60秒** |
| **SC-003** | 系统可承受 **200名用户** 在同一反馈窗口期内并发提交反馈，无数据丢失、无重复录入 |
| **SC-004** | 所有时间校验误差 **≤ 1秒**（完全依赖服务端时间，排除客户端干扰） |
| **SC-005** | 历史查询报表页面在 20 条/页分页条件下，接口响应时间 **≤ 2秒** |
| **SC-006** | cron 任务即使被重复触发 3 次，仍保证零重复记录（幂等性验证通过） |

## 十、假设

- 系统用户均通过微信小程序接入，拥有稳定的移动网络连接
- UniCloud 定时触发器服务可靠，触发延迟 ≤ 5 秒
- 基础数据模块（`base-area`、`base-point`、`base-dept`、`uni-id-users`）已完成开发并有数据可用
- 系统不需要离线操作能力，所有操作需在线完成
- 照片存储使用 UniCloud 内置云存储服务，无需外接 OSS
- 用户终端设备支持微信小程序拍照 API
- 日常活跃匹配关系配置总量 ≤ 200 条，日生成反馈记录总量 ≤ 500 条
