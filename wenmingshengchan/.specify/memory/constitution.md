# 文明生产专业管理系统 宪章

## 核心原则

### 一、代码质量与严谨性 (Code Quality & Rigor)
- **技术栈纯粹性**：强制使用 Vue 2 + VK UniCloud Router + 阿里云 UniCloud。所有涉及 UniCloud 操作必须严格使用 `vk-fun` 技能实现（参照 `database-examples.js` 和 `js-api-examples.js`）。
- **Dao 2.0 规范约束**：所有数据库交互必须通过继承 `BaseDao` 的类完成，业务部分的代码必须通过 `this.dao` 调用并透传 `db` 事务对象。不符合此规范的代码 PR 一律拒绝。
- **原子性与高并发安全**：针对计费、计数、状态变更等高关键操作，强制使用 `_.inc` 或 `updateAndReturn` 处理，绝对保障数据库处理的原子性。

### 二、测试标准与 TDD 驱动 (Testing & TDD)
- **强制 TDD（测试驱动开发）执行**：这是不可妥协的核心原则。在每次生成任何业务实现代码前，必须先规划并运行测试环境。
- **基于证据的准出机制**：所有的开发成果与接口功能逻辑，必须附带自动化测试/断言层面的通过证明才可声称完成并提交代码。

### 三、用户体验一致性 (UX Consistency)
- **核心能力与工具优先复用**：所有需要进行时间格式化、对象克隆、数组转树等常见操作的前端交互时，强制优先使用统一的底层 `vk.pubfn` 方法，杜绝引入同质化的三方库代码以提升打包加载速度和一致体验。
- **路由与鉴权一致性**：所有端内页面跳转必须统一强制使用内置并定制过状态检测机制的 `vk.navigateTo`。
- **前后端生态协同闭环**：小程序 UI 层注重互动与展示高效呈现（规范参考[这里](https://vkdoc.fsq.pub/client/changelog.html)）；中后台数据管理必须遵循 VK Admin 的风格及结构规则以保持整体运营操作界面的一致性（[参考](https://vkdoc.fsq.pub/admin/1/catalogue.html)）。

### 四、系统级性能要求 (Performance Architecture)
- **万能连表控制**：复杂的跨表及关联查询必须仅通过 `foreignDB` 数组实现；在涉及主表数据结构时，其结果整形**必须**组合使用 `getMain: true` 与 `getOne: true` 防止不必要的数据冗余或结构深嵌问题。
- **高阶索引及树型驱动获取**：检索层级的树形/分类数据时必须通过官方约定的 `treeProps` 递归规格实现；涉及数组对象的查询条件过滤，要求完全符合标准点聚类索引格式（如 `'arr.0'`），将复杂度化解在中后端计算层上。

## 项目结构与功能定义

### 1. 系统建设总目标
建立全面在线的文明生产专业管理系统，主要功能是落实：
- 现场点位状态监管
- 文明生产计划执行管理
- 文明生产专业信息管理
- 现场问题报备管理

### 2. 标准化模块
系统被界定为高度分离前后端的架构：

- **`client`**：微信小程序 (mp-client)
  - **位置**：`./mp-client`
  - **职责**：执行各类具体现场展现场景、互动汇报等C端类操，所有路径规则约束按照客户框架规范进行。
  
- **`admin`**：后台管理 (mp-admin)
  - **位置**：`./mp-admin`
  - **职责**：B端系统控制层，包含数据管理、权限控制、系统全局配置管理，全盘服从目录组织编排。
  
- **`unicloud`**：UniCloud 云函数
  - **位置**：`./mp-client/uniCloud-aliyun/cloudfunctions/router/service`
  - **职责**：承载云函数、数据库配置及各业务服务端核心逻辑。
  - **规范组织**：分别拆设 client 文件夹（供前台用）及 admin文件夹（供后台用），每一特定功能云函数归入对应的二级子文件夹并遵循命名规格文档指导。

### 3. 文档与提案规范
- **按「功能模块」拆分提案**：为保持文档的内聚性与可维护性，所有提案必须按功能模块拆分。
  - **业务提案命名**: `{模块名称}-提案.md`
  - **公共提案命名**: `公共核心-{模块名称}-提案.md`

## 治理机制与审查约束

这是整个软件生命周期和代码生产必须不折不扣遵循的管理规定：

- **【最高优先级】本宪法高于所有其他实践规范**：即使与某约定俗成的经验发生冲突，亦以本宪章定义为准。
- **【修改授权管理】**：任何对本宪章与技术标准的修订，须生成明确说明原由的文档记录、提交流程审批与老代码迁移计划。
- **【PR拦截红线机制】**：所有的 Pull Requests (PR) 和技术评审须完全验证 `DB & JS API` 规格合规性（即是否绝对尊从 `vk-fun` 规格与 Dao 2.0 范式），一旦违反则 PR 必须拒绝合并。
- **【无授权复杂性驳回】**：所有超出常规设计的“高复杂度”架构或代码炫技，必须配有清晰的架构分析文档验证合理理由。
- **【代码生命周期先决】**：执行**任何**实际代码构建或改动之前，强制进行测试前置分析与用例运行（即：**每次生成代码前必须先跑 TDD**）。
