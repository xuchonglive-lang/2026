# 任务列表：[功能名称]

**输入**：来自 `/specs/[###-feature-name]/` 的设计文档
**先决条件**：plan.md（必选），spec.md（用户故事必选），research.md，data-model.md，contracts/

**测试**：以下示例包含测试任务。测试是可选的——仅当功能规格或实施计划中明确要求时才包括它们。

**组织结构**：任务按用户故事分组，以便每个故事都能独立实施和测试。

## 格式：`[ID] [P?] [Story] 描述`

- **[P]**：可以并行运行（针对不同文件，无依赖关系）
- **[Story]**：该任务所属的用户故事（例如：US1、US2、US3）
- 在描述中包含确切的文件路径

## 路径约定

- **单体项目**：位于代码库根目录下的 `src/`, `tests/`
- **Web 应用**：`backend/src/`, `frontend/src/`
- **移动端应用**：`api/src/`, `ios/src/` 或 `android/src/`
- 下文所示的路径假定为单体项目 - 请根据 plan.md 结构进行调整

## 依赖关系与执行顺序

### 阶段间依赖

- **设置 (阶段 1)**：无依赖 - 可以立即开始
- **基础支撑 (阶段 2)**：依赖于设置的完成 - 它阻止了所有的用户故事实施
- **用户故事 (阶段 3+)**：全部依赖于基础支撑阶段的完成
  - 用户故事随后可以并行推进（如果人手充足）
  - 或按优先级降序连续执行（P1 → P2 → P3）
- **完善 (最终阶段)**：依赖于所有要求的用户故事已完成

### 用户故事依赖

- **用户故事 1 (P1)**：在基础支撑 (阶段 2) 后可启动 - 不依赖于其他故事
- **用户故事 2 (P2)**：在基础支撑 (阶段 2) 后可启动 - 可与 US1 整合，但应能独立测试
- **用户故事 3 (P3)**：在基础支撑 (阶段 2) 后可启动 - 可与 US1/US2 整合，但应能独立测试

### 用户故事执行内

- 测试（如果包含）必须在实现之前编写并出现失败状态
- 先处理模型，再处理服务 (Models before services)
- 先处理服务，再处理端点 (Services before endpoints)
- 先实现核心代码，再做集成
- 当前优先级的用户故事完成后，再走向下一个优先级

### 行动并行化机会

- 所有标记为 [P] 的设置任务均可并行运行
- 所有标记为 [P] 的基础任务均可并行运行（在阶段 2 中）
- 一旦基础阶段完成，所有用户故事可并行启动（视团队处理能力而定）
- 用户故事中标记为 [P] 的所有测试可并行运行
- 故事中标记为 [P] 的各个模型可并行处理
- 不同的团队成员可以并行处理不同的用户故事

## 实施策略

### MVP 优先（仅用户故事 1）

1. 完成 阶段 1：构建设置
2. 完成 阶段 2：基础支撑（极重要 - 阻断所有故事）
3. 完成 阶段 3：用户故事 1
4. **停止并校验**：独立测试用户故事 1
5. 如果就绪，进行部署/演示

### 增量交付

1. 完成 构建设置 + 基础支撑 → 基础架构就绪
2. 增加 用户故事 1 → 独立测试 → 部署/演示 (MVP 交付！)
3. 增加 用户故事 2 → 独立测试 → 部署/演示
4. 增加 用户故事 3 → 独立测试 → 部署/演示
5. 每个故事都在不破坏前面故事的前提下增加功能价值

### 并行团队策略

多人开发者参与时：

1. 团队共同完成 构建设置 + 基础支撑
2. 一旦基础支撑完成：
   - 开发者 A: 用户故事 1
   - 开发者 B: 用户故事 2
   - 开发者 C: 用户故事 3
3. 这些故事可独立完成和集成

## 注意事项

- [P] 级别的任务代表不同的文件，无冲突的相互依赖
- [Story] 标签将任务映射到具体的用户故事以保证可塑性
- 每个用户故事应当是可以被独立完成和测试的
- 实现目标代码前，验证测试代码会失败
- 在每个任务或逻辑分组后执行 Commit
- 可在任何检查点停下以独立验证用户故事情况
- 避免：模糊的任务描述、相同文件中的编辑冲突，以及破坏独立性的跨故事层依赖
