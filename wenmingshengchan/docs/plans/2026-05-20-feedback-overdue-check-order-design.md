# 反馈任务逾期清算与数据获取顺序重构设计文档

## 1. 背景与现状
目前在重控点位监督管理模块中，用户在首页或个人中心获取的待办数量（`getTodoCount`）是在执行逾期清算更新后通过 `count` 统计的，这保证了待办数的新鲜度。
但是在获取待办列表的云函数 `getTodoList` 中，当前的执行顺序存在严重逻辑缺陷：
- **先获取列表数据**：先执行了包含了 5 个表的复杂大联表查询 `vk.baseDao.selects`。
- **再在内存中判断逾期**：遍历查询出的结果进行物理时间计算，将已逾期的记录异步（无 `await`）发往数据库更新为 `2`（逾期）。
- **直接返回包含逾期记录的行**：因为是先查询，所以本次请求的 rows 中仍然返回了已逾期的行，导致用户列表中会出现本已过期的待办。

这造成了两个主要 Bug：
1. 数据不一致：首页显示待办数是 0（因为 `getTodoCount` 统计准确），而进入待办列表页却依然能看到被置为 expired 状态的任务堆在页面上，刷新后才消失。
2. 性能瓶颈：已过期的历史遗留任务在查询时依然被拉出来进行了复杂昂贵的 5 表关联查询。

## 2. 详细设计与重构方案

### 2.1 待办列表云函数 `getTodoList.js` 流程重写
重构为**先更新状态，再查询数据**的强同步逻辑：
1. **轻量获取任务判断过期**：
   - 过滤条件仅为当前用户 `assignee_ids: uid` 且 `status: 0`。
   - 限制返回字段 `fieldJson` 仅取 `_id, shift_type, shift_date, _add_time`，不带联表。
2. **计算逾期并强同步更新**：
   - 依据 `shiftMap` 的各班次 `feedback_end` 时间计算物理截止时间。
   - 收集已过期的任务 ID 数组 `overdueIds`。
   - 使用 `await vk.baseDao.update` 将它们状态修改为 `2`，确保该批数据在数据库中已写盘。
3. **安全查询有效待办列表**：
   - 执行原本的 `vk.baseDao.selects` 复杂联表查询。此时状态已更新，已过期的任务绝对不会被查出，保证列表清洁度与分页总数精确。
4. **注入未过期状态并返回**：
   - 只需为拉取出的未过期数据注入 `waiting` 或 `active` 的 `_feedback_status`。

### 2.2 待办数量云函数 `getTodoCount.js` 性能优化
- 优化第一阶段中拉取任务用于逾期判断的 `selects` 查询，增加 `fieldJson: { _id: 1, shift_type: 1, shift_date: 1, _add_time: 1 }`，减少数据库及网络传输开销。

## 3. 验收标准
1. 进入待办列表，所有已过截止时间的任务不再被查询并展示在列表上。
2. 首页的“待办重控”徽标数量与点击进入列表后的任务总数完全吻合。
3. 云服务接口调用开销与响应延迟显著降低。
