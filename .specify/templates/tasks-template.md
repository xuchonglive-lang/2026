# 任务清单：[FEATURE NAME]

**输入**: 来自 `/specs/[###-feature-name]/` 的设计文档
**前提条件**: plan.md (必填), spec.md (用户故事必填), research.md, data-model.md, contracts/

**测试**: 下方的示例包含测试任务。测试是可选的——仅在功能说明书中明确要求时才包含。

**组织方式**: 任务按用户故事分组，以便每个故事都能独立实现和测试。

## 格式：`[ID] [P?] [Story] 描述`

- **[P]**: 可并行执行（不同文件，无依赖关系）
- **[Story]**: 该任务所属的用户故事（例如：US1、US2、US3）
- 描述中包含确切的文件路径

## 路径规范

- **单项目**: `src/`, `tests/` 位于存储库根目录
- **Web 应用**: `backend/src/`, `frontend/src/`
- **移动端**: `api/src/`, `ios/src/` 或 `android/src/`
- 下方显示的路径假设为单项目——请根据 plan.md 的结构进行调整

## 依赖关系与执行顺序

### 阶段依赖

- **设置（第一阶段）**: 无依赖——可以立即开始
- **基础（第二阶段）**: 依赖于“设置”阶段的完成——阻塞所有用户故事
- **用户故事（第三阶段及以后）**: 全部依赖于“基础”阶段的完成
  - 用户故事可以并行推进（如果人手充足）
  - 或者按优先级顺序（P1 → P2 → P3）依次进行
- **打磨（最后阶段）**: 依赖于所有预定用户故事的完成

### 用户故事间的依赖

- **用户故事 1 (P1)**: 可以在基础阶段（第二阶段）完成后开始——不依赖于其他故事
- **用户故事 2 (P2)**: 可以在基础阶段（第二阶段）完成后开始——可能会与 US1 集成，但应能独立测试
- **用户故事 3 (P3)**: 可以在基础阶段（第二阶段）完成后开始——可能会与 US1/US2 集成，但应能独立测试

### 每个用户故事内部

- 测试（如果包含）必须在实现前编写并确保失败
- 模型先于服务
- 服务先于端点
- 核心实现先于集成
- 完成一个故事后再开始下一个优先级的故事

### 并行机会

- 所有标记为 [P] 的设置任务可以并行执行
- 所有标记为 [P] 的基础任务可以并行执行（在第二阶段内）
- 基础阶段完成后，所有用户故事可以并行开始（如果团队能力允许）
- 用户故事中所有标记为 [P] 的测试可以并行执行
- 故事中标记为 [P] 的模型可以并行执行
- 不同的团队成员可以并行处理不同的用户故事

## 实施策略

### MVP 优先（仅限用户故事 1）

1. 完成第一阶段：设置
2. 完成第二阶段：基础（关键——阻塞所有故事）
3. 完成第三阶段：用户故事 1
4. **停止并验证**: 独立测试用户故事 1
5. 如果就绪，进行部署/演示

### 增量交付

1. 完成 设置 + 基础 → 基础就绪
2. 添加用户故事 1 → 独立测试 → 部署/演示 (MVP!)
3. 添加用户故事 2 → 独立测试 → 部署/演示
4. 添加用户故事 3 → 独立测试 → 部署/演示
5. 每个故事都在不破坏先前故事的前提下增加价值

### 团队并行策略

对于多名开发人员：

1. 团队共同完成 设置 + 基础
2. 基础完成后：
   - 开发人员 A: 用户故事 1
   - 开发人员 B: 用户故事 2
   - 开发人员 C: 用户故事 3
3. 各个故事独立完成并集成

## 备注

- [P] 任务 = 不同文件，无依赖关系
- [Story] 标签将任务映射到特定的用户故事，以便追踪
- 每个用户故事都应能独立完成和测试
- 确保在实现前测试失败
- 在每个任务或逻辑组之后提交代码
- 在任何检查点停下来独立验证故事
- 避免：模糊的任务、同一个文件的冲突、破坏独立性的跨故事依赖
dependencies that break independence
