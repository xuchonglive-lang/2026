## 用户场景与测试 *(必填)*

### 用户故事 1 - 用户登录后自动加载租户上下文 (优先级: P1)

用户登录后，系统自动根据 `uni-id-users.tenant_id` 加载所属部门（租户）上下文。后续所有业务接口请求通过 `tenantFilter` 中间件自动追加 `tenant_id` 过滤条件，无需用户手动选择部门。前台页面顶部导航栏显示当前所属部门名称（PC端在右侧区域显示，H5端在标题处显示），普通用户无切换入口。

**优先级理由**: 租户隔离是整个平台的数据安全基座，所有业务模块（培训、信息、重点工作等）的数据查询和写入都依赖租户上下文。若此功能缺失，所有模块的数据安全无法保证。

**独立测试**: 用户A（部门1）和用户B（部门2）分别登录后，各自只能看到本部门的业务数据。可通过创建两个测试用户和两个测试部门，各自创建一条测试数据，交叉验证可见性。

**验收场景**:

1. **假设** 用户A属于"技术部"（`tenant_id: "dept_tech"`），**当** 用户A登录成功，**那么** 前台页面顶部导航栏右侧显示"技术部"，`store.$user` 中包含 `tenant_id` 和 `dept_path` 字段
2. **假设** 用户A属于"技术部"，**当** 用户A调用任意业务列表接口（如培训列表），**那么** 接口返回数据的每条记录 `tenant_id` 均为"dept_tech"或 `visibility` 为 `public`/`targeted`（且 `target_dept_ids` 包含"dept_tech"）
3. **假设** 用户A属于"技术部"，用户B属于"市场部"，用户B创建了一条 `visibility=private` 的培训数据，**当** 用户A调用培训列表接口，**那么** 返回结果中不包含用户B创建的该条数据
4. **假设** 用户A属于"技术部"（`dept_path: "/root/tech"`），上级部门"总部"（`dept_path: "/root"`）发布了一条 `visibility=public` 的通知，**当** 用户A查看信息列表，**那么** 可以看到该通知
5. **假设** 用户A的 `tenant_id` 为空（未分配部门），**当** 用户A登录后查看业务列表，**那么** 仅显示 `visibility=public` 的公共数据，并在页面顶部显示"未分配部门，请联系管理员"提示

### 用户故事 2 - 后台部门树形管理 (优先级: P1)

超级管理员在后台管理页面（`xc-admin/pages_plugs/system/dept/list.vue`）对部门（租户）进行全生命周期管理。页面采用左右分栏布局：左侧为 `el-tree` 部门树形导航（固定两级结构：集团→部门，支持关键词搜索过滤），右侧为选中部门的详情编辑表单（`vk-data-form`）+ 成员管理 Tab。

> **实施偏差记录**: 原设计为"无限层级 + 拖拽排序"，实际实施时确认为固定两级（集团 `dept_level=0` → 部室 `dept_level=10` / 车间 `dept_level=20`），无拖拽排序需求。

**优先级理由**: 部门结构是用户归属、权限分配和数据可见性的根基。必须在用户管理和权限管理之前完成。

**独立测试**: 管理员创建两级部门结构，验证 CRUD 和树形渲染的正确性。

**验收场景**:

1. **假设** 系统初始化，只有一个根节点"集团总部"（`dept_level=0`），**当** 管理员点击"新增"按钮，**那么** 弹出编辑表单，包含字段：部门名称（必填）、部门编码（必填，唯一）、上级部门（选择集团级部门）、部门层级（选择：部室/车间）、排序号（数字输入框，默认0）、状态（启用/停用开关，默认启用）、简介
2. **假设** 当前有"集团总部→生产部"结构，**当** 管理员在搜索框输入"生产"，**那么** 树形导航过滤显示匹配节点及其父级路径
3. **假设** 管理员选中"生产部"节点并点击"删除"，**当** 该部门下有成员时，**那么** 弹出阻止提示"该部门下存在成员，无法删除"
4. **假设** 管理员修改"生产部"状态为"停用"，**当** 保存成功，**那么** 树形节点显示灰色+停用标签，该部门下所有用户登录后跳转至 `dept-disabled` 提示页

### 用户故事 3 - 部门成员管理 (优先级: P1)

管理员在部门详情页中管理部门成员，可查看当前部门所有用户列表、将用户添加到当前部门、将用户从当前部门移除。一个用户只能归属一个部门。

**优先级理由**: 用户与部门的绑定关系是租户隔离的数据基础。

**独立测试**: 将用户从部门A移到部门B后，用户登录时应加载部门B的上下文。

**验收场景**:

1. **假设** 管理员选中"技术部"节点，**当** 点击"成员管理"tab，**那么** 右侧下方显示该部门成员列表（`vk-data-table`），列包含：头像、姓名、手机号、角色、加入时间
2. **假设** 管理员点击"添加成员"按钮，**当** 弹出用户选择器（仅显示"未分配部门"的用户），**那么** 选择用户后更新该用户的 `tenant_id` 和 `dept_path`
3. **假设** 管理员选中一个已在"技术部"的用户并点击"移除成员"，**当** 确认移除，**那么** 该用户的 `tenant_id` 置空，`dept_path` 清空，用户下次登录时看到"未分配部门"提示
4. **假设** 管理员尝试将一个已属于"市场部"的用户添加到"技术部"，**当** 操作确认，**那么** 弹出警告"该用户当前属于「市场部」，确认调整到「技术部」？"，确认后更新用户归属

### 用户故事 4 - 超级管理员切换部门视角 (优先级: P2)

超级管理员（`dept_level=0`）在后台顶部导航栏通过 `el-select` 下拉选择器切换当前操作部门视角。切换时调用 `switchView` 云函数将选择持久化到用户记录（`uni-id-users.selected_view_tenant_id`），`tenantFilter` 中间件从 `userInfo` 读取该值自动过滤业务数据。非集团用户不显示选择器。

> **实施偏差记录**: 原设计用 `el-cascader` + `localStorage`，实际改为 `el-select`（按部室/车间分组）+ 数据库持久化方案。原因：1) `el-cascader` 在两级扁平结构中多此一举；2) `localStorage` 方案无法穿透 `vk-data-table` 的内部请求，改为数据库持久化后中间件直接从 `userInfo` 读取。

**优先级理由**: 管理员需按部门维度审核和管理各部门的业务数据。

**独立测试**: 管理员切换到不同部门后，页面列表数据立即刷新且仅显示目标部门数据。

**验收场景**:

1. **假设** 超级管理员（`dept_level=0`）登录后台，**当** 应用初始化完成（`$app.inited=true`），**那么** 顶部导航栏面包屑右侧出现部门选择器（`el-select`），按部室/车间分组显示，集团级自身不在选项中
2. **假设** 管理员选择"生产部"，**当** 选择确认，**那么** 调用 `switchView` 云函数将 `selected_view_tenant_id` 写入用户记录，提示"已切换部门视角"
3. **假设** 管理员切换到"生产部"视角后刷新页面或重新登录，**当** DeptSelector 初始化，**那么** 调用 `getMyLevel` 从数据库恢复上次选择
4. **假设** 管理员清空选择器（清除选中），**当** 确认清除，**那么** 调用 `switchView` 传空值，删除用户记录的 `selected_view_tenant_id`，恢复全局视角
5. **假设** 非集团用户（`dept_level=10/20`）登录后台，**当** 页面加载完成，**那么** 不显示部门选择器
6. **假设** 用户切换登录账号（从集团到非集团），**当** `$user.userInfo._id` 变化，**那么** DeptSelector 自动重置并重新初始化

### 用户故事 5 - 数据可见性配置 (优先级: P2)

所有业务模块（培训、信息传达、重点工作等）在发布数据时可配置可见性：`public`（所有部门可见）、`private`（仅本部门可见，默认值）、`targeted`（指定下级部门可见，可多选部门）。前台查询时 `tenantFilter` 中间件自动根据当前用户的 `tenant_id` 和 `dept_path` 计算可见数据范围。

**优先级理由**: 跨部门信息共享和数据隔离的核心机制，被所有业务模块复用。

**独立测试**: 分别创建三种可见性的数据，用不同部门用户验证可见性计算是否正确。

**验收场景**:

1. **假设** 培训管理页面的课程编辑表单中，**当** 管理员展开"可见性设置"区域，**那么** 显示单选框组（公开所有部门 / 仅本部门可见 / 指定部门可见），选择"指定部门可见"时展开部门多选树形选择器（仅显示当前部门的下级部门）
2. **假设** "总部"发布一条 `visibility=public` 的培训课程，**当** "技术部"用户和"市场部"用户分别查看培训列表，**那么** 两者都能看到该课程
3. **假设** "技术部"发布一条 `visibility=targeted, target_dept_ids=["前端组ID", "后端组ID"]` 的课程，**当** "前端组"用户查看列表，**那么** 可以看到；**当** "设计组"用户查看列表，**那么** 不可见
4. **假设** "技术部"发布一条 `visibility=private` 的课程，**当** "市场部"用户或"技术部"下级部门用户查看列表，**那么** 均不可见，仅"技术部"直属用户可见
5. **假设** 管理员将一条数据从 `public` 修改为 `private`，**当** 保存成功后其他部门用户刷新列表，**那么** 该数据从列表中消失

### 用户故事 7 - 部门管理操作权限控制 (优先级: P1) ⚠️ 新增

> **问题发现**：实施过程中发现作业区（`dept_level=20`）账号能修改部室（`dept_level=10`）的部门信息。根因：`admin/system/dept/sys/` 下所有云函数仅依赖 VK 内置的 `loginFilter` 校验登录态，**不校验操作者的角色和 `dept_level`**，同时 `tenantFilter` 已跳过 `admin/system/` 路径，导致任何后台登录用户可执行全部部门管理操作。

部门管理操作必须根据操作者的 `dept_level` 进行权限分级控制：

- **集团级（`dept_level=0`）**：可操作所有部门（增删改查、成员管理、视角切换）
- **部室级（`dept_level=10`）**：仅可查看本部门信息，不可修改任何部门
- **车间级（`dept_level=20`）**：仅可查看本部门信息，不可修改任何部门

**验收场景**:

1. **假设** 作业区用户（`dept_level=20`）通过 API 直接调用 `admin/system/dept/sys/update`，**当** 请求到达云函数，**那么** 返回 `{ code: -1, msg: '权限不足' }`
2. **假设** 部室用户（`dept_level=10`）调用 `addMember`，**当** 请求到达，**那么** 返回权限不足
3. **假设** 集团级用户（`dept_level=0`）调用 `update`，**当** 请求到达，**那么** 正常执行

---

### 边界情况

- 用户 `tenant_id` 为空时：仅显示公共数据，业务功能入口显示"请联系管理员分配部门"
- 部门被停用时：该部门用户可登录但跳转至 `pages/error/dept-disabled` 提示页
- 固定两级结构：集团（`dept_level=0`）→ 部室（`dept_level=10`）/ 车间（`dept_level=20`），不支持无限层级
- 删除部门时：禁止删除有子部门或成员的部门，需先清空
- `targeted` 可见性选择了大量部门（>50）时：查询性能处理（索引优化）
- 部门编码唯一性校验：新增/修改时实时校验，已存在则提示
- DeptSelector 切换登录：监听 `$user.userInfo._id` 变化自动重置
- `tenantFilter` 跳过 `admin/system/` 路径：系统管理表不需要租户过滤

## 需求 *(必填)*

### 功能需求

- **FR-001**: 系统必须在用户登录成功后，将 `tenant_id`、`dept_path`、`tenant_name`、`dept_level` 写入 `store.$user` 状态管理
- **FR-002**: 系统必须提供 `tenantFilter` 中间件（`middleware/modules/tenantFilter.js`），对业务云函数请求自动追加租户过滤条件（跳过 `user/pub/` 和 `admin/system/` 路径）。集团用户检查 `userInfo.selected_view_tenant_id` 注入过滤；普通部门用户注入 `$or` 条件（`tenant_id` / `visibility=public` / `targeted+target_dept_ids`）
- **FR-003**: 系统必须提供部门 CRUD 云函数（`service/admin/system/dept/sys/`），字段包含：`name`、`code`（唯一）、`parent_id`、`dept_path`（自动生成）、`dept_level`（0=集团/10=部室/20=车间）、`leader_id`、`sort_num`、`status`（0/1）、`description`
- **FR-004**: 系统使用固定两级部门结构（集团→部室/车间），通过 `dept_level` 字段区分层级
- **FR-005**: 后台部门管理页使用 `el-tree` 组件，支持：节点展开/折叠、关键词过滤（`filter-node-method`）、节点点击事件（加载右侧详情和成员管理）
- **FR-006**: 后台提供集团级管理员专属的 `el-select` 部门视角切换，按部室/车间分组显示。切换时调用 `switchView` 云函数持久化到 `uni-id-users.selected_view_tenant_id`，中间件从 `userInfo` 读取
- **FR-007**: 数据可见性三级配置（public/private/targeted），对应 `VisibilitySetter` 组件，`visibility`、`target_dept_ids` 作为通用字段内嵌到所有业务数据集合
- **FR-008**: 部门成员管理保证一个用户只能归属一个部门（跨部门调动时弹出确认提示）
- **FR-009**: ~~拖拽移动部门~~ （已移除，固定两级结构无需拖拽）
- **FR-010**: 前台顶部导航栏显示当前用户的部门名称（PC端在用户头像左侧，H5端如空间不足可省略）
- **FR-011**: `xc-tenants` 集合索引：`parent_id`、`code`（唯一）、`status`、`dept_level`
- **FR-012**: 前台部门信息页展示部门层级路径面包屑、部门信息卡片（名称/编码/负责人/简介/层级标签）
- **FR-013** ⚠️ **新增**: 部门管理云函数（`add`/`update`/`del`/`sort`/`addMember`/`removeMember`/`switchView`）必须校验操作者的 `dept_level`，仅 `dept_level === 0`（集团级）允许执行写操作
- **FR-014** ⚠️ **新增**: `getMyLevel` 云函数从数据库直接查询当前用户的 `dept_level` 和 `selected_view_tenant_id`，返回服务端计算的 `canSwitchView` 布尔值
- **FR-015** ⚠️ **新增**: 部门停用后，前台 `App.vue` 的 `checkTenantContext` 方法检测到 `status=0` 时跳转至 `pages/error/dept-disabled` 页面

### 关键实体

- **xc-tenants（租户/部门表）**: `_id`、`name`、`code`（唯一）、`parent_id`（根部门为null）、`dept_path`（如 `"/root_id/dept_id"`）、`dept_level`（0=集团/10=部室/20=车间）、`leader_id`、`sort_num`、`description`、`status`（0=停用 1=启用）、`created_by`、`created_at`、`updated_by`、`updated_at`
- **uni-id-users（扩展字段）**: `tenant_id`（所属部门ID）、`dept_path`（冗余）、`tenant_name`（冗余）、`dept_level`（冗余，用于中间件快速判断）、`selected_view_tenant_id`（集团用户专用，部门视角切换持久化）

### 可衡量的结果

- **SC-001**: 不同部门用户登录后，业务数据 100% 按租户隔离，通过交叉测试 0 条数据泄露

- **SC-005**: 部门拖拽移动后，所有子部门和关联用户的 `dept_path` 在 3 秒内批量更新完成
- **SC-006**: 可见性过滤逻辑准确率 100%（public 全可见、private 仅本部门、targeted 仅指定部门）
